1. Chọn pattern: augmented LLM, workflow, agent & subagent

  • Đơn giản nhất đủ dùng: một biến đổi/request, yêu cầu ổn định → một augmented LLM call kèm context → dấu hiệu đề "catalog note" Q10
  • Sectioning ≠ voting: sectioning chia subtask độc lập chạy song song; voting lặp cùng một việc để tăng tin cậy → "4 check độc lập, turnaround" Q48
  • Prompt chaining: chia theo subtask (extract → eligibility → merit → draft), mỗi bước xử lý cả hồ sơ; không chia theo kích thước chunk Q49
  • Orchestrator-workers: chỉ khi subtask thay đổi theo request, quyết lúc chạy; việc cố định thì là overhead Q10, Q48
  • Agent tự trị: số bước không biết trước → giới hạn iteration tối đa + checkpoint người duyệt → "lặp mãi tốn tiền" Q41
  • Subagent ≠ mặc định: dùng cho việc song song độc lập hoặc khám phá rộng làm ngập context; bước tuần tự phụ thuộc thì làm trực tiếp Q44, Q62
  • Subagent không thừa kế history: chép toàn bộ history vào là mất lợi ích cô lập, tốn token gấp đôi Q44, Q62
  • Messages API ≠ Managed Agents: Messages API khi cần loop tùy biến, kiểm soát chi tiết; Managed Agents cho task dài, bất đồng bộ Q18

2. Tích hợp: MCP, direct API, agent-to-agent & tool surface

  • MCP = lớp tái sử dụng: nhiều app hiện tại/tương lai dùng chung; tool đổi thường, team chủ quản bảo trì một chỗ Q3, Q17
  • Direct API: một đường gọi tất định trong pipeline mình sở hữu, không cần model hay tool discovery Q3, Q17
  • Agent-to-agent: agent độc lập của hai tổ chức phối hợp, thương lượng động, không lộ hệ thống nội bộ → "trust boundary" Q3, Q17
  • Tải tool lai: 5 tool dùng thường nạp sẵn, đuôi dài discover on demand (tool search tool) Q8
  • MCP connector allowlist: chỉ bật tool cần dùng; mỗi definition tốn input token và làm chọn tool kém → "40 tool, dùng 5" Q31
  • Proxy free-text: mất interface có kiểu, khó validate; không bỏ được bloat Q31

3. Prompt, context & cấu hình Claude Code

  • XML tag: bọc instructions, context, examples, input riêng → "Claude làm theo text trong ví dụ" Q6
  • Prefill ≠ được hỗ trợ: 4.6+ trả 400; thay bằng structured outputs hoặc nêu format trong system prompt Q9
  • Trust hierarchy: system prompt có quyền chỉ dẫn, tool result là dữ liệu; chỉ dẫn đặt trong tool result bị làm theo chập chờn Q19
  • Context editing: tool result clearing xóa tool result cũ phía server, giữ nguyên message Q16
  • Bảo bỏ qua ≠ gỡ khỏi context: token vẫn chiếm window, vẫn gây context rot Q16, Q22, Q31
  • CLAUDE.md phình to: chỉ giữ rule áp dụng rộng; workflow thỉnh thoảng dùng chuyển sang skill nạp on demand Q22, Q54
  • Skill description: nêu cả làm gì và khi nào dùng; chỉ name + description nạp sẵn → "Skill hiếm được gọi" Q28
  • Phạm vi subagent: dùng chung commit vào .claude/agents/; cá nhân ở ~/.claude/agents/; project thắng khi trùng tên Q30
  • Settings local: giá trị riêng máy cho một project → file local bị git ignore, đè shared project Q60
  • Prompt leak: system prompt có thể lộ; chống leak làm giảm chất lượng; bí mật để sau tool/server Q11

4. RAG: chunking & embedding

  • Chunk overlap: chunk cố định cắt giữa điều khoản → thêm overlap để đoạn qua ranh giới nằm nguyên trong một chunk Q13
  • Chunk tìm kiếm ≠ chunk sinh: small-to-big — khớp chunk nhỏ, đưa parent section cho model Q21
  • Embedding chuyên ngành: thuật ngữ pháp lý biểu diễn kém → model như voyage-law-2, re-index toàn bộ Q57
  • Tăng số chunk / hạ threshold: thêm nhiễu, không đảm bảo lấy đúng đoạn kề Q13, Q21, Q57
  • Index cả tài liệu / chunk lớn: vector bị pha loãng, mất precision Q13, Q21
  • Identifier chính xác (số hiệu, citation) → hybrid BM25 + embedding Q57

5. Model, chi phí, latency & độ tin cậy API

  • Model ID cố định: weights không đổi theo ID; serving stack chỉ gây chênh nhỏ; nâng cấp là sự kiện migration có chủ đích Q20
  • Routing theo độ khó: câu đơn giản sang Haiku, troubleshooting phức tạp sang model mạnh Q40
  • Vision + tool use có ở mọi tier: khác nhau ở suy luận, tốc độ, giá → eval tier nhỏ trước Q56
  • Latency, cost do model quyết: sửa prompt hai sprint không đổi → thử tier rẻ hơn, chạy lại eval Q47
  • Message Batches API: giảm 50%, cho request độc lập, kết quả nhận sau hàng giờ; không cho streaming hay lượt phụ thuộc Q32, Q59
  • Cache pre-warming: gửi warm-up trước khi traffic trở lại; TTL 5 phút hoặc 1 giờ; breakpoint không kéo dài TTL Q35
  • Token counting API: đếm input trước khi gửi, miễn phí; input vượt window trả 400, không tự cắt Q42
  • Streaming: giảm perceived latency, không đổi nội dung → "chờ lâu, không được giảm chất lượng" Q63
  • stop_reason: max_tokens = bị cắt; thêm gate kiểm hoàn chỉnh trước khi forward Q50
  • Retry một tầng: SDK retry 2 lần, exponential backoff, theo retry-after; bỏ vòng retry tức thì của app Q61

6. Guardrail, bảo mật & human oversight

  • Approval gate fail closed: không có người duyệt = từ chối; không tự duyệt, không chạy rồi log Q5
  • Giới hạn tổng: cap mỗi giao dịch không chặn số lượng → aggregate/rate limit trong hệ thống hoàn tiền (circuit breaker) Q12
  • Oversight theo profile hành động: nhiều, rủi ro thấp, đảo ngược được → review mẫu ngẫu nhiên định kỳ Q14
  • Input screening: tool chạy giữa lượt trước khi có output → classifier chặn jailbreak trước model Q52
  • Disable ≠ delete API key: disable đảo ngược được cho triage; delete vĩnh viễn; expiration cố định khi tạo Q33
  • Draft-and-review: Claude phân tích, soạn đề xuất; underwriter có tên duyệt → giữ accountability Q37
  • GDPR Article 22: thông báo quyết định tự động, cho khiếu nại, đường người xem xét lại Q39
  • Hallucination còn sót: grounding, citation, "không biết" giảm nhưng không xóa hết → giữ người kiểm cho quyết định an toàn Q58
  • Ngăn chặn ≠ phát hiện: log, đối soát tháng, review sáng hôm sau không chặn được thiệt hại Q5, Q12, Q52

7. Đánh giá, metric & công bằng

  • Khớp lịch sử ≠ công bằng: 94% agreement đo độ trung thành với quyết định có thể thiên lệch → audit + so outcome theo nhóm Q2
  • Bias từ base model: vẫn giảm được ở tầng ứng dụng (prompt, ví dụ đa phương ngữ) rồi đo lại gap Q29
  • Data leakage: eval dùng lại few-shot trong prompt → điểm ~100%; thay bằng held-out case độc lập Q23
  • A/B test đồng thời: chia traffic ngẫu nhiên; so trước/sau theo tuần bị nhiễu bởi thời gian Q25
  • Bias ≠ variance: grader cùng model gây bias hệ thống → dùng model khác để chấm; lấy trung bình chỉ giảm nhiễu Q27
  • Eval trước khi sửa prompt: success criteria + eval set để so phiên bản prompt Q46
  • Metric hữu ích: p95 < 2 giây trên query đại diện; chi phí trung bình mỗi request hoàn tất Q38
  • Ngưỡng achievable: không đặt 100%; dựa baseline/benchmark + đường escalate cho lỗi còn lại Q53

8. Observability & telemetry

  • Correlation ID: truyền qua mọi subagent, tool call thành trace liên kết; SDK có parent_tool_use_id Q24
  • Hai tầng telemetry: metric/trace rẻ cho mọi session; full payload chỉ lấy mẫu + khi lỗi Q26
  • Metric ≠ log/event: metric là tổng theo thời gian; muốn xem từng prompt, tool → bật OTEL_LOGS_EXPORTER Q45
  • Tail latency: mean che phần chậm → p95, p99 tách theo loại request Q55
  • Staging replay: agent không tất định, phụ thuộc dữ liệu live → thường không tái hiện được Q24, Q26

9. Discovery, giao tiếp & vòng đời dự án

  • Bằng chứng mới ≠ chờ họp: kiến trúc sai thì báo sponsor ngay: bằng chứng, đề xuất mới, chi phí, tiến độ Q1
  • Decision package: so các phương án theo tiêu chí đã thống nhất, nêu khuyến nghị kèm trade-off Q4
  • Discovery: quy trình hiện tại (khối lượng, điểm đau, người dùng) + ràng buộc pháp lý, privacy, truy cập Q7
  • Baseline: đo quy trình hiện tại trước khi đặt mục tiêu "tiết kiệm thời gian" Q43
  • Kết thúc design: chốt pattern kiến trúc + cách đánh giá; runbook, nhãn output production thuộc pha sau Q51
  • Dashboard xanh, khiếu nại tăng: phân tích khiếu nại tìm chiều chất lượng thiếu, re-baseline với sponsor Q15
  • SLA theo workload: assistant tương tác cần latency; batch đêm cần throughput, deadline Q36
  • Transformation pillar: năng lực trước đây không khả thi; nhanh hơn = efficiency, rẻ hơn = cost Q34

13. Mẹo làm bài thi

  • Đúng cơ chế cho đúng lớp: hỏi lỗi nằm ở retrieval, generation, context, hay giao hàng; loại phương án sửa lớp khác Q57, Q63
  • Temperature hầu như luôn sai: không đổi format, sự thật, tốc độ, chi phí, hay drift model.
  • "Nâng tier mạnh nhất" hiếm khi đúng: không sửa trust model, vòng lặp, context thiếu, hay jailbreak.
  • Bảo model "bỏ qua" không gỡ token: loại phương án chỉ dẫn thay cho cấu hình nạp.
  • "Select two" thường là hai mặt: sampling + error-triggered Q26, phân tích + re-baseline Q15, user + project scope Q30.
  • Đo trước, đổi sau: baseline, eval set, A/B đồng thời; loại "launch rồi đo".
  • Câu giao tiếp: chọn minh bạch, kịp thời, có khuyến nghị và trade-off; loại im lặng, trì hoãn, đổ dữ liệu thô.
  • Kiểm soát cứng ngoài model: limit trong hệ thống, gate fail closed, classifier đầu vào.

Học đáp án đúng chỉ giải được đúng câu đó. Hiểu vì sao từng đáp án sai lại sai giúp nhận diện được cả họ câu hỏi tương tự, kể cả khi đề đổi cách hỏi. Mỗi dòng dưới đây là một câu, liệt kê các đáp án sai và lý do sai thật sự — đúc kết từ chính phần giải thích của đề, không phải suy đoán.

CâuĐáp án sai & vì sao sai
Q1
  • Chờ buổi steering review định kỳ: trong lúc chờ, ngân sách tiếp tục đổ vào kiến trúc đã biết là không phù hợp; bằng chứng quan trọng phải báo ngay khi xác nhận
  • Giữ kiến trúc cũ, ghi biến động input vào backlog: coi sai lệch nền tảng là lỗi nhỏ; workflow cố định sẽ hỏng ở đúng mục đích cốt lõi, và sponsor mất quyền quyết định
  • Âm thầm làm lại, tự gánh chi phí trong ngân sách: che giấu thay đổi quan trọng với người chịu trách nhiệm ngân sách, tiến độ; sớm muộn cũng lộ qua chênh lệch chi phí
Q2
  • Huấn luyện tới gần 100% agreement rồi tuyên bố công bằng: càng khớp lịch sử càng tái tạo trung thành bias có sẵn, làm rủi ro mạnh thêm
  • Bỏ đo định lượng, chỉ dùng nhận định chuyên gia: công bằng đo định lượng được (so outcome theo nhóm); lỗi là chọn sai đại lượng, không phải việc dùng metric
  • Coi quyết định lịch sử là ground truth, chứng nhận theo 94%: chính là ngụy biện đang xét; quyết định của người không trung lập, có thể chứa thiên lệch hệ thống
Q3
  • MCP cho agent của hai công ty phối hợp mà không lộ hệ thống nội bộ: đó là trường hợp agent-to-agent qua trust boundary; đưa hệ thống nội bộ thành tool server cho bên kia là điều ràng buộc cấm
  • MCP cho job chuyển bản ghi giữa database theo lịch, không có model: chuyển dữ liệu tất định không cần tool discovery; tích hợp trực tiếp trong code đơn giản hơn
Q4
  • Trình bày mọi kiến trúc chi tiết như nhau, không khuyến nghị: chi tiết dàn trải che mất quyết định; không khuyến nghị là bỏ trách nhiệm đưa ra nhận định chuyên môn
  • Chỉ trình bày kiến trúc được chọn: tước thông tin hội đồng cần để làm vai trò phê duyệt; khi phát hiện có phương án bị giấu, niềm tin giảm
  • Đưa dữ liệu benchmark thô, hoãn khuyến nghị: dồn việc tổng hợp cho người không có bối cảnh; nhiệm vụ của architect là biến bằng chứng thành khuyến nghị
Q5
  • Để model tự đánh giá rủi ro rồi chạy nếu thấy an toàn: tự duyệt loại bỏ phán đoán độc lập mà gate được đặt ra để cung cấp
  • Tự động duyệt để pipeline không bị chặn: biến gate thành fail-open; chính các hành động rủi ro lại chạy mà không ai xem
  • Chạy rồi log cho reviewer xem sáng hôm sau: chuyển kiểm soát ngăn chặn thành phát hiện; hành động khó đảo ngược đã xảy ra rồi
Q6
  • Hạ temperature để model đọc prompt sát chữ hơn: temperature chỉ chỉnh độ ngẫu nhiên của output, không giúp phân biệt chỉ dẫn với ví dụ
  • Lặp lại toàn bộ chỉ dẫn ở cuối prompt: tăng độ nổi bật nhưng không đánh dấu ranh giới ví dụ; text ví dụ vẫn lẫn với chỉ dẫn
  • Bỏ các worked example: mất một kỹ thuật điều khiển format đáng tin cậy; vấn đề là thiếu cấu trúc, không phải có ví dụ
Q7
  • Soạn sẵn system prompt và few-shot example: là sản phẩm của pha build; làm ở discovery neo team vào giải pháp trước khi hiểu vấn đề
  • Chọn tier model và cấu hình production: là quyết định design dựa trên yêu cầu chất lượng, latency, chi phí — những yêu cầu chưa có ở discovery
Q8
  • Nạp cả 50 tool, dựa vào prompt caching: caching giảm chi phí và độ trễ, nhưng token cache vẫn chiếm context window nên chất lượng vẫn giảm
  • Chuyển toàn bộ catalog sang discovery on demand: 5 tool dùng gần như mọi request phải discover mỗi lần, thêm latency mà không tiết kiệm context
  • Chia tool cho hai agent, mỗi agent nạp một nửa: thêm chi phí routing, phối hợp; mỗi agent vẫn mang khối lớn definition không liên quan
Q9
  • Prefill một phần assistant message: Claude 4.6 trở đi không hỗ trợ prefill, request trả lỗi 400
  • Đặt temperature 0 để luôn ra JSON hợp lệ: temperature không ràng buộc cấu trúc; model có thể lặp lại cùng một JSON hỏng mỗi lần
Q10
  • Orchestrator giao subtask cho worker chuyên biệt: chỉ hợp khi subtask thay đổi theo request; việc đồng nhất, đơn giản thì phân rã là overhead thuần
  • Agent tự trị tự lên kế hoạch cho mỗi cuốn sách: các bước giống nhau mọi lần; tự trị chỉ thêm latency, chi phí, khó đoán
  • Workflow nhiều bước có gate giữa các call: một mô tả ra một ghi chú ngắn không có subtask đáng tách; chaining chỉ thêm bước
Q11
  • Mã hóa system prompt at rest ngăn trích xuất: model vẫn nhận plaintext lúc inference; leak đi qua output, kênh mà mã hóa at rest không chạm tới
  • System prompt bị ẩn khỏi quá trình sinh nên không thể lộ: system prompt là input model attend tới; không có rào chắn kiến trúc ngăn tái hiện nội dung
Q12
  • Xuất bản ghi hoàn tiền sang data warehouse đối soát hàng tháng: kiểm soát phát hiện, thấy thiệt hại sau vài tuần; không chặn được sự cố diễn ra trong vài giờ
  • Dặn agent trong system prompt hoàn tiền thận trọng, thưa: chỉ dẫn prompt mang tính khuyên; bị bỏ qua khi model bị thao túng hay trục trặc
  • Hạ cap mỗi giao dịch từ $100 xuống $50: giảm cỡ từng lần nhưng không giới hạn số lần; hàng nghìn lần $50 vẫn gây lỗ lớn
Q13
  • Index cả tài liệu thay vì chunk: một vector gộp nhiều điều khoản khác nhau, giảm mạnh độ chính xác truy xuất
  • Lấy nhiều chunk hơn mỗi query: không đảm bảo chunk kề được xếp hạng cao; làm ngập context bằng chunk không liên quan
  • Hạ similarity threshold: cho thêm nhiễu toàn corpus, không ưu tiên kéo đúng chunk kề hoàn thiện điều khoản
Q14
  • Chỉ xem quyết định khi downstream báo misroute: thuần phản ứng; misroute âm thầm và drift dần không tạo khiếu nại nên không có tín hiệu hệ thống
  • Model thứ hai duyệt từng quyết định: không phải human oversight; hai model có thể chung điểm mù nên lỗi hệ thống lọt qua cả hai
  • Người duyệt từng quyết định trước khi gửi: dành cho hành động không đảo ngược, tác động lớn; ở đây phá hiệu quả và gây rubber-stamping
Q15
  • Đưa dashboard đạt chuẩn làm bằng chứng khiếu nại không mang tính hệ thống: bảo vệ thước đo thay vì kết quả; giả định metric phản ánh đủ trải nghiệm, trái với thực tế
  • Giảm tần suất báo cáo để làm phẳng các đợt khiếu nại: che tín hiệu thay vì điều tra, làm yếu vòng phản hồi của quan hệ SLA
Q16
  • Dặn model bỏ qua tool result cũ: nội dung vẫn nằm trong request, vẫn chiếm window và có thể làm model mất tập trung
  • Giảm max output tokens: chỉ giới hạn phần model sinh ra mỗi lượt, không giảm input tích tụ
  • Bật prompt caching: đổi chi phí và độ trễ, nhưng nội dung cache vẫn tính đủ vào context window
Q17
  • Agent-to-agent cho một call tất định trong pipeline đêm tự sở hữu: là trường hợp tích hợp API trực tiếp; không có agent đối tác hay trust boundary
  • Agent-to-agent cho nhiều app nội bộ truy cập tool của một hệ thống chung: truy cập chuẩn hóa, tái sử dụng là việc của MCP; ở đây là app gọi tool, không phải agent thương lượng
Q18
  • Messages API cho cả hai workload: workload bất đồng bộ dài không cần kiểm soát chi tiết; team phải tự dựng và vận hành harness
  • Managed Agents cho cả hai workload: harness dựng sẵn đánh đổi kiểm soát chi tiết, mâu thuẫn với yêu cầu custom agent loop
  • Ghi hai đường là thay thế được, kỹ sư tự chọn: hai bề mặt khác nhau; bỏ trống là né quyết định kiến trúc, dẫn tới triển khai không nhất quán
Q19
  • Viết lại chỉ dẫn trong tool result mạnh mẽ hơn: vấn đề là vị trí, không phải câu chữ; tool result bị coi là dữ liệu dù nhấn mạnh thế nào
  • Đặt temperature 0 để làm theo tất định: temperature không đổi mức thẩm quyền model gán cho từng phần input
  • Nâng lên tier mạnh nhất: năng lực không đổi trust model; model mạnh còn tách chỉ dẫn khỏi dữ liệu nhất quán hơn
Q20
  • Chọn tier mạnh nhất vì ít bị cập nhật: không có quan hệ giữa tier và tần suất thay thế; versioning như nhau ở mọi tier
  • Đặt temperature 0 để output tất định, không drift: temperature chỉ chỉnh sampling trong một model, không đảm bảo tất định, không liên quan độ ổn định model
  • Re-validate hàng tuần để bắt cập nhật weights ngầm: sai tiền đề — Anthropic không đổi weights của model ID hiện có
Q21
  • Embed lại với chunk lớn hơn nhiều: chunk lớn pha loãng vector, mất độ chính xác truy xuất mà đề yêu cầu giữ
  • Bảo model tự dựng lại bước còn thiếu từ kiến thức huấn luyện: dễ bịa bước sửa chữa, mất grounding vào tài liệu thật
  • Tăng mạnh số chunk trả về: làm ngập context, chỉ may rủi bắt được bước kề, tốn token và thêm nhiễu
Q22
  • Tách thành nhiều file import theo chủ đề: import chỉ là cách tổ chức; file import vẫn nạp vào context đầu session
  • Sắp xếp lại một file với header rõ hơn: giúp đọc dễ hơn nhưng không giảm số token nạp mỗi session
  • Thêm chỉ dẫn bỏ qua phần không liên quan: chỉ dẫn không ngăn nội dung được nạp; token vẫn chiếm context và gây suy giảm
Q23
  • Tăng temperature khi chạy eval để giảm ghi nhớ: chỉ thêm ngẫu nhiên vào output; bộ test vẫn bị nhiễm dữ liệu
  • Đổi sang model lớn hơn để chấm chặt hơn: grader không phải vấn đề; chấm chặt trên dữ liệu nhiễm vẫn đo việc chép ví dụ trong prompt
  • Thêm ví dụ chép từ system prompt vào bộ test: làm leakage nặng hơn, điểm càng bị thổi phồng
Q24
  • Log phản hồi cuối của supervisor cùng request gốc: chỉ ghi nơi thấy lỗi, bỏ mất các bước trung gian nơi lỗi phát sinh
  • Tăng log chi tiết cho từng subagent, lưu ở kho riêng: không có định danh chung để nối bản ghi của một request qua các agent
  • Tái hiện lỗi trên staging, chạy từng subagent: agent không tất định, phụ thuộc tool và dữ liệu production, nên replay thường không ra lỗi cũ
Q25
  • So điểm eval offline của bản mới với metric production tuần trước: hai phân phối khác nhau, đo bằng cách khác nhau; còn khó diễn giải hơn so tuần với tuần
  • Đóng băng mọi deployment khác trong tuần test: chỉ kiểm soát thay đổi của team; traffic, hành vi người dùng, mùa vụ vẫn khác giữa hai tuần
  • Kéo dài mỗi cửa sổ đo lên một tháng: giảm nhiễu ngẫu nhiên nhưng không loại khác biệt hệ thống giữa hai giai đoạn
Q26
  • Chỉ log phản hồi cuối, bỏ bước trung gian: lỗi agent thường phát sinh ở tool call, retrieval, delegation; bỏ chúng là mất bằng chứng chẩn đoán
  • Dời log payload chi tiết sang staging: nhiều lỗi phụ thuộc dữ liệu live và trạng thái hệ thống ngoài mà staging không tái tạo được
Q27
  • Tăng temperature của grader: thêm phương sai ngẫu nhiên, không bỏ độ lệch hệ thống; grader lệch vẫn lệch trung bình
  • Lấy trung bình hai lượt chấm cùng model: giảm nhiễu nhưng không giảm bias; cả hai lượt mang cùng độ lệch
  • Rút gọn rubric: rubric chi tiết mới làm LLM grader ổn định; bớt tiêu chí làm tăng phán đoán tùy ý và bias
Q28
  • Rút ngắn phần thân chỉ dẫn của Skill: thân chỉ được đọc sau khi Skill đã kích hoạt, không ảnh hưởng quyết định có gọi hay không
  • Đưa toàn bộ chỉ dẫn vào system prompt mọi request: bỏ cơ chế nạp on demand, quay lại chi phí token mỗi request mà team muốn tránh
  • Tăng temperature để model ưu tiên Skill: temperature chỉnh sampling, không ảnh hưởng việc khớp request với Skill
Q29
  • Chuẩn hóa mọi bài nộp về một dạng ngôn ngữ: có thể làm mất ý nghĩa, giọng điệu; che chênh lệch ở đầu vào thay vì xử lý biến thể hợp lệ
  • Chấp nhận giới hạn, chờ base model mới: tầng ứng dụng không bất lực; chờ đợi để tác hại công bằng tồn tại trong production vô thời hạn
  • Hạ temperature cho nhất quán giữa các nhóm: temperature không đổi cách model xử lý khác nhau giữa phương ngữ; vẫn kém đều cho một nhóm
Q30
  • Dán chỉ dẫn subagent vào CLAUDE.md dùng chung: CLAUDE.md nạp mọi session, làm phình context và giảm tuân thủ rule quan trọng
  • Bảo từng dev tự cài subagent của team ở user scope: gây lệch cấu hình, bản cũ khác nhau; người mới phải cài tay
Q31
  • Bọc server sau một tool free-text proxy mọi lệnh: mất interface có kiểu để validate; giấu bloat trong lớp mờ thay vì loại bỏ
  • Dặn trong system prompt bỏ qua tool không cần: definition vẫn nằm trong request, vẫn tốn token và cạnh tranh khi chọn tool
  • Lên tier mạnh hơn chịu được catalog lớn: chữa triệu chứng với giá cao hơn; definition thừa vẫn tốn token mỗi call
Q32
  • Streaming để bị tính ít output token hơn: streaming chỉ đổi cách giao token, không đổi số token sinh ra hay tính tiền
  • Hạ temperature để model trả lời nhanh hơn: temperature không phải đòn bẩy giá; tính tiền theo token thực tế
  • Chuyển hết sang model nhỏ nhất không đánh giá: có thể giảm chất lượng phân loại, làm thay đổi kết quả workload; phải eval trước
Q33
  • Rút ngắn hạn dùng của key bị gắn cờ: expiration chọn lúc tạo, không đổi được sau đó; cũng không thu hồi ngay
  • Tắt cảnh báo tới khi analyst xác nhận compromise: key bị lộ thật vẫn hoạt động suốt thời gian chờ, nới rộng phơi nhiễm
  • Khôi phục key đã xóa khi xác nhận false positive: xóa là vĩnh viễn, key bị archive và không kích hoạt lại được
Q34
  • Giảm chi phí inference bằng prompt caching: hạ đơn giá cho cùng năng lực, thuộc pillar cost
  • Rút ngắn khoảng 30% thời gian proofreading: cùng quy trình chạy nhanh hơn, thuộc pillar efficiency
Q35
  • Thêm cache breakpoint để đoạn cache sống lâu hơn: breakpoint chỉ đổi độ chia nhỏ cache, mỗi entry vẫn hết hạn theo TTL 5 phút hoặc 1 giờ
  • Đưa request đầu sau quãng nghỉ sang model nhỏ hơn: vẫn xử lý toàn bộ prompt chưa cache; cache không dùng chung giữa model, hành vi lại không nhất quán
  • Rút ngắn system prompt: chỉ thu nhỏ cache miss chứ không ngăn được; còn có thể mất chỉ dẫn cần thiết
Q36
  • Bỏ latency khỏi thỏa thuận, chỉ cam kết accuracy, uptime: assistant tương tác mất cam kết hiệu năng nó thực sự cần
  • Dùng chung mục tiêu dưới 2 giây cho cả hai: ép batch đêm theo latency không ai trải nghiệm, tốn chi phí vô ích
  • Đưa pipeline batch lên tier nhanh nhất: uốn kiến trúc theo một SLA không phù hợp, có thể hy sinh chất lượng phân loại
