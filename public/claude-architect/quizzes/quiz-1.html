1. Prompt engineering

  • Few-shot (multishot): 3–5 ví dụ sát use case thật, đa dạng, phủ edge case, bọc trong <example> Q1
  • Ví dụ gần giống hệt nhau: model bắt chước cả chi tiết ngẫu nhiên; một ví dụ là quá hẹp Q1
  • Rule ≠ data: bọc input người dùng trong thẻ riêng, nói rõ "là dữ liệu, không phải chỉ dẫn" → dấu hiệu đề "chỉ dẫn trong tin nhắn khách ghi đè" Q3
  • Tách suy luận khỏi kết luận: reasoning và verdict trong hai thẻ riêng → giữ độ chính xác CoT, parser vẫn đọc được Q35
  • Giải thích lý do của rule: "TTS sẽ đọc output" giúp model khái quát tốt hơn lệnh cấm trơn Q50
  • Hallucination ≠ lỗi định dạng: cho phép trả "không tìm thấy", chỉ trả lời từ tool result → dấu hiệu đề "bịa số đăng ký" Q58
  • Temperature: chỉ đổi độ ngẫu nhiên lấy mẫu, không đổi grounding, ranh giới tin cậy hay nội dung xuất ra Q3, Q35, Q58

2. Context window, prompt caching & RAG

  • Caching ≠ tiết kiệm window: token cache vẫn tính đủ vào context window; caching chỉ giảm chi phí và độ trễ Q13, Q46
  • Prompt too long: phải gửi ít token hơn — retrieval, compaction, context editing; không phải thêm breakpoint/TTL 1 giờ Q13
  • Prefix lặp lại lớn: đặt nội dung ổn định lên đầu rồi cache → giảm cả TTFT lẫn chi phí input Q33
  • Cache + nạp theo nhu cầu: cache rule chung, chỉ nạp guide cần cho request; cache không xóa token thừa Q37
  • API stateless: app phải lưu và gửi lại lịch sử hội thoại; cache, thinking, window lớn không thay được Q40
  • Subagent khám phá: đọc file trong context riêng, chỉ trả tóm tắt → giữ context chính Q46
  • Corpus nhỏ, ít đổi: đưa nguyên vào prompt + cache prefix; chưa cần RAG Q19
  • Thang retrieval: full context → chunk vector search → hybrid BM25 + embedding + rerank, leo khi dữ liệu buộc Q19
  • Metadata filter: lọc theo thuộc tính phân loại (mẫu máy bay) trước khi xếp hạng → không trả nhầm tài liệu gần giống Q38
  • RAG thời gian thực: cắt passage không liên quan + giảm effort cho câu đơn giản sau khi eval Q51

3. Tool catalogue & progressive discovery

  • Vừa window ≠ không hại: context rot — token càng nhiều, accuracy/recall càng giảm dù chưa chạm giới hạn Q14
  • Progressive discovery: catalogue lớn, mỗi request dùng ít tool → nạp theo nhu cầu Q14
  • Discovery ≠ mặc định: ít tool, dùng mọi request, vừa context → nạp hết từ đầu; discovery chỉ thêm bước Q10
  • Capability bloat: gộp tool trùng lặp thành bộ nhỏ, mục đích không chồng lấn → dấu hiệu đề "4 tool tìm chuyến bay" Q22
  • Audit bloat: tìm tool không bao giờ được gọi + đo tỷ lệ window mà tool definitions chiếm Q27
  • Một tool free-text chung: anti-pattern, mất schema có kiểu, che khuất việc chọn tool Q22

4. Chọn mẫu kiến trúc: workflow & agent

  • Workflow ≠ agent: workflow theo code path định trước; agent tự điều hướng khi bước không đoán trước Q7, Q18
  • Evaluator-optimizer: tiêu chí rõ + sửa lặp cải thiện đo được → một call viết, một call chấm Q7
  • Voting ≠ sectioning: voting chạy cùng task nhiều lần để tăng độ tin cậy; sectioning chạy subtask độc lập để giảm latency Q18, Q28
  • Orchestrator-workers: subtask không liệt kê trước, khác mỗi request → dấu hiệu đề "số file không biết trước" Q39
  • Prompt chaining: chuỗi bước cố định, output bước trước vào bước sau; điểm dừng cho người duyệt Q55, Q56
  • Một call quá tải: bỏ sót subtask, suy luận nông dần → chia nhỏ, chain call, truyền structured output Q56
  • Extended thinking/subagent: không tạo điểm dừng giữa các bước để người phê duyệt Q55
  • Chia việc LLM vs code: LLM hiểu văn bản tự do, soạn thư; code làm số học, rule khớp cố định Q62

5. Tích hợp, chọn model tier & chi phí

  • Direct API: một team, một consumer, call tất định → gọi Messages API trong code pipeline Q6
  • MCP ≠ A2A: MCP cho nhiều app cần truy cập tool chuẩn hóa; A2A cho agent tự chủ khác bên phối hợp Q6, Q45
  • MCP connector: chỉ tới server public qua HTTP; server stdio nội bộ cần MCP client chạy trong app Q45
  • Message Batches API: khối lượng lớn, không ai chờ, ưu tiên rẻ → batch bất đồng bộ Q41
  • Ràng buộc thật: job đêm dư latency → accuracy là ràng buộc, lên tier mạnh hơn Q25
  • Chọn tier: model rẻ nhất đạt chuẩn chất lượng, có eval liên tục; so cost per completed task Q43
  • Model mismatch: prompt đã tinh chỉnh kỹ vẫn suy luận nông → thử tier mạnh hơn và so kết quả Q59
  • Claude Code tự kiểm: cho check chạy được (test suite) để lặp tới khi pass, giảm giám sát tay Q44

6. Guardrail, xác thực & human-in-the-loop

  • Hướng dẫn ≠ cơ chế ép buộc: prompt/CLAUDE.md là advisory; bất biến đặt vào hook, permission, code Q2, Q9, Q26, Q31
  • Hook PostToolUse: matcher Edit|Write chạy formatter sau mỗi edit thành công; không phủ lệnh Bash Q2
  • Permission deny rule: client ép buộc, deny xét trước allow; đặt trong project settings đã commit Q31
  • Least privilege tại tầng thực thi: tài khoản DB read-only chặn UPDATE dù bị prompt injection Q26
  • Output filter: chặn công thức bí mật trước khi tới user; không bắt được bản diễn đạt lại Q9
  • Gate phê duyệt ở app: Claude chỉ phát tool request, app thực thi → duyệt trước khi chạy Q8
  • Duyệt có ý nghĩa: hiện argument, đích, tác động; chỉ tên tool thì thành đóng dấu Q34
  • Validate output tại ranh giới: kiểm hoàn chỉnh + schema trước handoff, retry hoặc gắn cờ Q5
  • Workload identity federation: đổi identity nền tảng lấy credential ngắn hạn; bỏ key dùng chung của cá nhân Q15
  • App Attest: app iOS/macOS gọi thẳng Claude nhận token ngắn hạn theo workspace, không nhúng key Q48
  • Indirect prompt injection: red-team chỉ dẫn độc trong email bên ngoài mà agent đọc và có tool Q63

7. Tuân thủ, quyền riêng tư & AI có trách nhiệm

  • GDPR erasure: xóa lan khắp log, retrieval index, analytics store; cần data lineage theo data subject Q12
  • Retention schedule ≠ xóa theo yêu cầu: hết hạn tự động vẫn là đã lưu; erasure phải thực hiện ngay cho từng người Q12, Q57
  • ZDR theo từng tính năng: batch, Agent Skills lưu theo chính sách chuẩn; kiểm từng feature trước khi dùng Q57
  • Fairness: bỏ thuộc tính bảo vệ chưa đủ; đo kết quả theo nhóm nhân khẩu để lộ proxy variable Q21
  • Quyết định tự động hệ trọng: giải thích có ý nghĩa + đường xem xét bởi người Q29

8. Evaluation, A/B test & observability

  • Grading hỗn hợp: code kiểm field tất định, LLM-judge có rubric hiệu chuẩn với người cho tone Q11
  • Số lượng > độ chính xác từng case: 1.500 case tự động mạnh hơn 50 case chấm tay Q17
  • Success criteria: cụ thể, đo được, có ngưỡng, phương pháp, tập test → "< 0,1% bị flag" Q16
  • Streaming lỗi giữa chừng: HTTP 200 rồi error event trong stream → xử lý và log event đó Q20
  • Trace từng bước: input, output, tool result mỗi bước mỗi request → quy lỗi về đúng bước Q30
  • Giám sát chất lượng: eval tự động trên mẫu production; latency/token/lỗi không bắt được hồi quy Q47
  • Một biến mỗi thử nghiệm: đổi prompt + model cùng lúc thì không quy được nguyên nhân Q42
  • A/B test: định trước cỡ mẫu và tiêu chí significance, chạy đủ rồi mới quyết Q53

9. Discovery, stakeholder & vòng đời giải pháp

  • Discovery: phỏng vấn, quan sát người làm việc thật, không chỉ quản lý Q23
  • Mâu thuẫn tiêu chí thành công: tổ chức buổi hòa giải thành tiêu chí chung đo được trước design Q24
  • Chỉ số kỹ thuật ≠ business case: trình bày giá trị đo được so với baseline trước pilot Q4
  • SLA: biến "nhanh và chính xác" thành latency percentile + ngưỡng accuracy; không cam kết zero error Q32
  • Giao tiếp với board: nói theo tiêu chí họ quan tâm (độ mới, chi phí) + bằng chứng eval Q36
  • Giữ kỳ vọng: báo cáo đều theo SLA đã thống nhất + đưa feedback vào eval set Q49
  • Decision record (ADR): bối cảnh, phương án đã xét, trade-off → trả lời câu hỏi "vì sao" lâu dài Q52, Q61
  • Sau go-live: cần giai đoạn monitoring & iteration có owner rõ Q60
  • Monitoring & iteration: so với baseline đã thống nhất, ưu tiên cải tiến theo lỗi production Q54

13. Mẹo làm bài thi

  • Yêu cầu "luôn luôn/không bao giờ": chọn cơ chế tất định ngoài model, loại phương án sửa wording.
  • Đề nói "trước khi": loại log, audit hàng tuần, review sau — đó là kiểm soát phát hiện.
  • Hỏi "mỗi cơ chế giải quyết gì?": caching–chi phí, window–sức chứa, temperature–ngẫu nhiên, batch–giá.
  • Mẫu đơn giản nhất đủ dùng: agent tự chủ hiếm khi đúng nếu các bước đã biết trước.
  • Đọc ràng buộc thật của workload: không ai chờ thì latency không quan trọng Q25, Q41.
  • "Select two" là hai mặt bổ trợ: sectioning/voting Q28, input/effort Q51, báo cáo/feedback Q49.
  • Đổi model là phương án cuối: chỉ đúng khi prompt đã tinh chỉnh kỹ mà vẫn thiếu năng lực Q59.
  • Câu stakeholder: đáp án đúng đo được, có baseline, thống nhất trước, ghi lại thành tài liệu.

  • Chỉ một ví dụ chọn kỹ cho prompt ngắn: dưới mức khuyến nghị 3–5; model không biết đặc điểm nào là thiết yếu, còn chi phí token đã có caching bù
  • Mọi ví dụ gần giống hệt nhau: model bám vào chi tiết ngẫu nhiên chung giữa các ví dụ; hướng dẫn yêu cầu đa dạng, không lặp lại
Q2
  • Nhờ dev nhắc lại Claude mỗi khi bỏ qua: biến con người thành vòng ép buộc cho bước lẽ ra tự động, chữa triệu chứng mỗi lần
  • Thêm nhấn mạnh IMPORTANT: tăng mức tuân thủ nhưng chỉ dẫn vẫn là advisory, vẫn còn lần bỏ sót
  • Lặp rule ở nhiều chỗ trong file chỉ dẫn: làm file phình, file quá dài khiến rule bị lạc; không đổi bản chất advisory
Q3
  • Chèn lại rule ngay sau tin nhắn khách: tốn token mỗi request, tin nhắn khách vẫn trông như chỉ dẫn, không được đánh dấu là data
  • Đặt tin nhắn khách lên đầu prompt: chỉ đổi vị trí, không đổi danh tính; mẹo đặt tài liệu dài lên đầu là để tăng recall
  • Đặt temperature về 0: temperature điều khiển ngẫu nhiên lấy mẫu, không quyết định phần nào của prompt có thẩm quyền
Q4
  • Dẫn điểm benchmark hơn model đối thủ: là đầu vào chọn model, không gắn với kết quả hiệu suất hay chi phí của tổ chức
  • Nhấn mạnh tiết kiệm token nhờ prompt caching: chỉ giảm chi phí vận hành của chính giải pháp, không nói giá trị tạo ra cho doanh nghiệp
  • Khoe kiến trúc agentic tinh vi và tier model cao: mô tả cách xây, không phải giá trị đem lại; anti-pattern trình diễn năng lực
Q5
  • Job đối soát hằng đêm chạy lại ingestion lỗi: sửa sau khi lỗi đã lan xuống hệ thống, giữ nguyên độ trễ hàng giờ
  • Tăng max output để không bị cắt: trần output không phải bảo đảm; record thiếu field vẫn đi tiếp vì không có cổng kiểm tra
  • Chuyển sang tier model mạnh nhất: giảm tần suất chứ không loại bỏ; kiến trúc vẫn chuyển output chưa kiểm tra xuống dưới
Q6
  • Bọc thành agent tự chủ dùng agent-to-agent: A2A dành cho agent độc lập qua ranh giới tổ chức; ở đây không có agent thứ hai
  • Đăng ký toolset MCP toàn công ty để tái dùng sau: xây hạ tầng cho consumer giả định, đề bài nói không app nào khác dùng
  • Mở dữ liệu pipeline qua MCP server: MCP đáng công khi nhiều app cần truy cập; một consumer, một call cố định thì chỉ thêm bảo trì
Q7
  • Một call với tiêu chí nhúng thành few-shot: chỉ cải thiện bản nháp đầu, không có bước critique-revise mà đề đã đo là có ích
  • Agent tự chủ tự lên chiến lược sửa: quy trình đã biết và lặp lại được; tự chủ chỉ thêm chi phí và khó đoán
  • Voting song song chọn bản điểm cao nhất: chỉ chọn giữa các bản nháp đầu, không bản nào được sửa theo feedback
Q8
  • Chỉ dẫn system prompt bảo model xin phép: advisory, model có thể bỏ qua hoặc bị thao túng; không phải kiểm soát cứng
  • Audit log được compliance xem hằng tuần: kiểm soát phát hiện, xem sau khi email đã gửi và record đã đổi
  • Model tự đánh giá rủi ro và dừng khi không chắc: giao quyết định cho chính thành phần bị quản lý; yêu cầu là duyệt mọi hành động
Q9
  • Giảm độ ngẫu nhiên lấy mẫu: kiểm soát độ biến thiên, không chống thao túng; model tất định vẫn bị dụ tiết lộ
  • Log mọi response và audit mẫu hằng tuần: phát hiện sau khi người dùng đã thấy công thức, không ngăn được
  • Viết lại system prompt mạnh hơn, viết hoa: vẫn advisory; red-team đã chứng minh chỉ dẫn bị vượt qua
Q10
  • Áp dụng discovery vì tối thiểu context là mặc định: coi kỹ thuật là giáo điều; tool ít và luôn dùng thì không có gì để hoãn
  • Nạp theo nhu cầu, dựa caching bù bước tra cứu: caching không loại bỏ lượt model thêm để tìm tool; discovery vốn không cần
  • Chia 4 tool cho các subagent chuyên biệt: 4 tool luôn cần không gây vấn đề chọn tool; thêm chi phí điều phối vô ích
Q11
  • Cho người chấm mọi output trên rubric chung: chất lượng cao nhưng chậm, đắt, không mở rộng; người nên dùng để hiệu chuẩn judge
  • So khớp chính xác với thư viện tin nhắn đã duyệt: văn bản tự do có nhiều cách viết đúng; tin nhắn mới hợp lệ bị chấm trượt
  • Một LLM judge chấm cả field lẫn tone: chậm, đắt, kém tin cậy hơn code cho phần so khớp field tất định
Q12
  • Xóa transcript khỏi DB hội thoại rồi đóng yêu cầu: dữ liệu đã lan sang retrieval index và analytics store, xóa một bản là chưa đủ
  • Rút ngắn retention của analytics store: lịch hết hạn chung, không xử lý yêu cầu cụ thể của từng người kịp thời
  • Thêm chỉ dẫn bảo model quên người dùng: prompt chỉ đổi hành vi lúc suy luận, không xóa dữ liệu đã lưu
Q13
  • Chuyển corpus vào system prompt vì không tính window: sai; system prompt, message, tool và output đều tính vào window
  • Thêm cache breakpoint để loại từng đoạn khỏi window: breakpoint chỉ định phần nào được cache, không bớt token nào khỏi window
  • Dùng cache TTL một giờ: TTL ảnh hưởng tỷ lệ hit và chi phí, không liên quan context window
Q14
  • Chuyển sang tier có context window lớn hơn: nội dung đã vừa; thêm sức chứa không đảo ngược suy giảm do context rot
  • Bật prompt caching cho toàn bộ catalogue: caching đổi chi phí, độ trễ, không đổi lượng token chiếm context
  • Tăng max output token: chỉ giới hạn độ dài response, vấn đề nằm ở phía input bị loãng
Q15
  • Mã hóa key khi lưu và hạn chế tooling deploy: khi nạp vào service key vẫn là secret dài hạn dùng chung; gắn tài khoản cá nhân
  • Xoay key hằng tháng qua secrets manager: thu hẹp cửa sổ lộ nhưng vẫn là secret tĩnh chung, vẫn gắn với một người
  • Gắn ID riêng cho request mỗi service: chỉ là kiểm soát phát hiện, không đổi cách xác thực
Q16
  • Đếm khiếu nại an toàn tháng đầu sau launch: chỉ số trễ, chỉ có sau khi người dùng đã gặp output hại; phụ thuộc hành vi báo cáo
  • Cam kết định tính "luôn an toàn, phù hợp": là ý định, không có ngưỡng và phương pháp đo nên không làm gate được
  • Dùng điểm benchmark an toàn của model: đo model gốc, không đo hệ thống lắp ráp với prompt, tool, dữ liệu riêng
Q17
  • Chấm tay 50 case chuyên gia: mẫu quá nhỏ để phát hiện hồi quy có ý nghĩa, và chấm tay quá chậm để chạy thường xuyên
  • Luân phiên hai cách giữa các release: công cụ đo thay đổi mỗi lần, kết quả không so sánh được
  • Chấm tay 50 case xoay vòng: mỗi release vẫn chỉ 50 case, hồi quy ở case chưa xem bị bỏ sót nhiều chu kỳ
Q18
  • Agent tự chủ tự quyết bước review: đánh giá một bài theo chính sách cố định là task biết trước; tự chủ thêm chi phí
  • Chuỗi call tuần tự, bước sau sửa phán quyết trước: kiểm duyệt không phải task nhiều bước; thêm latency, không có phán quyết độc lập
  • Một call ra phán quyết, call hai critique và sửa: evaluator-optimizer để trau chuốt bản nháp, không cho nhiều góc nhìn độc lập
Q19
  • Chia chunk và vector search: thêm embedding, index, refresh và lỗi bỏ sót chunk cho vấn đề context không tồn tại
  • Tóm tắt handbook thành bản ngắn: mất chi tiết, không trả lời được câu hỏi cụ thể dù bản đầy đủ vừa context
  • Hybrid BM25 + embedding + rerank: dành cho corpus lớn; thừa kỹ thuật khi toàn bộ đã vừa context window
Q20
  • Tăng giới hạn retry của SDK: SDK đã retry lỗi thấy được; lỗi giữa stream không được giám sát phát hiện
  • Tăng response timeout: vấn đề không phải timeout mà lỗi trong stream đã mở không được ghi nhận
  • Tắt streaming để lỗi hiện thành mã HTTP: hy sinh độ trễ cảm nhận thấp; lỗ hổng nằm ở cách đọc stream
Q21
  • Kiểm mẫu nhỏ tìm ngôn từ phân biệt: bất công trong xếp hạng mang tính thống kê, không hiện trong văn bản; mẫu nhỏ không bắt được
  • Xác minh lại không còn thuộc tính bảo vệ: fairness through unawareness đã biết là không đủ, proxy variable vẫn tái tạo thiên lệch
  • Dựa vào alignment của model gốc: không bảo đảm công bằng cho ứng dụng, dữ liệu, quyết định cụ thể; phải đo ở tầng ứng dụng
Q22
  • Chuyển sang tier mạnh nhất để quản catalogue: chữa triệu chứng với chi phí cao hơn; vẫn trả token cho 58 định nghĩa
  • Một tool free-text chung tự dispatch: mất interface có kiểu, khó bắt call sai; anti-pattern đã được nhận diện
  • Mở rộng mô tả mọi tool kèm ví dụ: thêm context mà không bỏ được trùng lặp; lỗi chọn tool và chi phí vẫn còn
Q23
  • Gửi manager checklist tính năng để xếp hạng: giả định đã biết đúng tính năng; vẫn giới hạn ở góc nhìn gián tiếp
  • Làm prototype từ yêu cầu quản lý rồi lấy feedback: neo mọi người vào giải pháp có thể sai, đẩy chi phí phát hiện sai lệch về sau
  • Chốt yêu cầu theo quản lý vì họ sở hữu ngân sách: nắm ngân sách không có nghĩa biết chi tiết vận hành; bỏ sót edge case
Q24
  • Thiết kế hai biến thể cho mỗi phòng: gấp đôi công thiết kế, eval, bảo trì để che một bất đồng chưa được xem xét
  • Chọn định nghĩa của người cấp cao hơn: cấp bậc không làm yêu cầu đúng; xung đột quay lại lúc launch
  • Vào design ngay, giải quyết ở UAT: thiết kế theo mục tiêu mơ hồ; UAT thành tranh cãi mục tiêu, đắt hơn nhiều
Q25
  • Giữ model nhanh, chạy hai lần rồi so: gấp đôi chi phí; lỗi do thiếu năng lực thường lặp lại ở cả hai lần
  • Thêm few-shot cho tới khi bằng tier mạnh: không thể dựa vào prompt để lấp khoảng cách năng lực với văn bản pháp quy phức tạp
  • Stream output từng phần: chỉ cải thiện độ trễ cảm nhận, vô nghĩa với batch qua đêm; không giảm lỗi
Q26
  • Đặt temperature về 0: không đổi khả năng tuân thủ khi bị tấn công; model tất định vẫn bị dụ viết lệnh ghi
  • Viết lại system prompt với cảnh báo viết hoa: vẫn là hướng dẫn xác suất; test đã chứng minh bị vượt qua
  • Log mọi query và review hằng tuần: phát hiện sau khi dữ liệu đã bị sửa, không ngăn được
Q27
  • Gắn cờ tool được dùng nhiều nhất: phân bố dùng tập trung là bình thường, không nói gì về các tool còn lại
  • Xem các call trả kết quả lớn cần cắt: là vấn đề xử lý kết quả lúc chạy, không phải số lượng tool đăng ký
Q28
  • Mỗi bước dùng output bước trước: đó là prompt chaining; bước phụ thuộc thì không chạy đồng thời được
  • Model điều phối tự xác định subtask mỗi request: đó là orchestrator-workers; parallelization cần subtask biết trước
Q29
  • Log nội bộ cho auditor xem hằng quý: người nộp đơn không thấy; không giải thích, không có đường khiếu nại
  • Công bố chi tiết kiến trúc model: không giải thích vì sao đơn cụ thể bị từ chối, không cho cách phản đối
  • Thông báo quyết định tự động, không kháng nghị: chỉ một phần minh bạch và xóa luôn quyền khiếu nại
Q30
  • Tăng khảo sát hài lòng người dùng: tín hiệu trễ, thô; không cho biết bước nào gây lỗi
  • Cảnh báo khi token hằng ngày lệch trung bình: đo chi phí, lưu lượng; câu trả lời sai vẫn tốn token bình thường
  • Giám sát uptime và CPU: phát hiện sự cố hạ tầng, không phát hiện output sai
Q31
  • Nhắc lại trong system prompt mỗi subagent: vẫn là chỉ dẫn; luồng chính và subagent có sẵn không bị quản
  • Đưa lên đầu CLAUDE.md và đánh dấu IMPORTANT: CLAUDE.md vẫn là context advisory, không bảo đảm
  • Chép vào CLAUDE.md cấp user của từng dev: vẫn là hướng dẫn, phụ thuộc từng người tự duy trì
Q32
  • Ký wording mơ hồ, lượng hóa sau khi có dữ liệu: launch theo thỏa thuận không ai đánh giá được; kỳ vọng ngầm cứng lại
  • Chấp nhận vì điều khoản lỏng có lợi cho team: mơ hồ chắc chắn dẫn đến tranh chấp; diễn giải của sponsor thành chuẩn
  • Cam kết zero lỗi: LLM là xác suất, không ai bảo đảm được; chắc chắn vi phạm hợp đồng
Q33
  • Chia khối policy thành nhiều request tuần tự: nhân số call, tăng độ trễ; vẫn xử lý cùng lượng nội dung, phân mảnh context
  • Chuyển sang tier nhỏ nhất: giảm giá token nhưng vẫn xử lý lại toàn khối mỗi lần; rủi ro giảm chất lượng
  • Giảm max output: không tác động TTFT hay chi phí input do prefix lặp lớn
Q34
  • Thêm người duyệt thứ hai cùng prompt: hai người đóng dấu thay vì một; không ai có thông tin để đánh giá
  • Thay bằng log xem hằng quý: biến kiểm soát ngăn chặn thành phát hiện; hành động hại chạy ngay
  • Chuyển sang tier model mạnh hơn: có thể bớt request xấu nhưng bước duyệt vẫn mù
Q35
  • Giảm temperature để bỏ reasoning: temperature không quyết định nội dung; reasoning xuất hiện vì prompt yêu cầu
  • Few-shot chỉ có verdict trơn: khiến Claude bỏ suy luận hiển thị, mất phần tăng độ chính xác
  • Bỏ chỉ dẫn suy luận từng bước: output sạch nhưng mất cải thiện accuracy đã đo được
Q36
  • Nói RAG là chuẩn ngành, không cần giải thích: né đúng câu hỏi được đặt ra, không có bằng chứng phù hợp với tổ chức
  • Giảng chi tiết embedding, vector search: vùi quyết định trong chi tiết kỹ thuật mà board không đánh giá được
  • Chuyển câu hỏi cho cố vấn kỹ thuật: bỏ trách nhiệm giải thích quyết định với người chịu trách nhiệm
Q37
  • Giữ mọi guide, cache cả khối: chỉ giảm giá token, vẫn trả cache-read và lấp window bằng 19 guide thừa
  • Fine-tune model trên các guide: mỗi lần cập nhật phải train lại, không có vết chỉ dẫn đang áp dụng
  • Tóm tắt rule tuân thủ: có thể làm mất yêu cầu bắt buộc; không xử lý 20 guide gửi thừa
Q38
  • Đổi embedding model lớn hơn: quy trình các mẫu máy bay gần như giống chữ, embedding vẫn gần nhau
  • Chỉ dẫn Claude bỏ qua quy trình mẫu khác: vá ở tầng prompt cho lỗi tầng pipeline; xác suất, rủi ro trong bảo dưỡng
  • Tăng số chunk truy xuất: kéo thêm bản gần trùng mâu thuẫn, trông chờ model tự phân xử
Q39
  • Parallelization với tập subtask định trước: cần subtask biết trước; đề nói không liệt kê trước được
  • Vòng evaluator-optimizer: trau chuốt một output, không giải bài toán phân rã động
  • Prompt chain cố định cho mọi request: việc khác nhau mỗi request; chain cố định sẽ thiếu bước hoặc thừa bước
Q40
  • Bật extended thinking: suy luận sâu hơn trên context được gửi, không khôi phục lượt cũ không có trong request
  • Bật prompt caching để API giữ lượt cũ: caching không lưu trạng thái hội thoại; nội dung vẫn phải được gửi
  • Model có context window lớn hơn: lịch sử không được gửi thì window lớn cũng vô ích
Q41
  • Chuyển sang tier mạnh nhất: giá token cao nhất, tăng đúng chi phí cần giảm mà không có bằng chứng cần
  • Cache nội dung từng tài liệu: mỗi tài liệu chỉ xử lý một lần, không có cache hit
  • Request đồng bộ song song + retry mạnh: trả giá chuẩn, tự vận hành concurrency, throttling cho tính real-time không ai cần
Q42
  • Tăng traffic tới khi có significance: giải quyết nhiễu, không tách được hai thay đổi gây nhiễu nhau
  • Chấp nhận và tiếp tục gộp thay đổi: lặp lại vấn đề mỗi chu kỳ; khi hồi quy không biết phần nào gây ra
  • Quy cho nâng cấp model: là đoán, không đo; prompt có thể chiếm phần lớn hoặc âm
Q43
  • Mặc định tier mạnh nhất: thay đo lường bằng giả định; tier nhỏ đạt chuẩn thì trả thêm vô ích
  • Chọn model mới nhất: ngày phát hành không phải tiêu chí; bản mới không chắc tốt hơn cho workload cụ thể
Q44
  • Prompt duyệt thủ công trước mỗi edit: duyệt việc chạy, không phải tính đúng; tăng giám sát thay vì giảm
  • Chuyển sang tier mạnh nhất: giảm tỷ lệ lỗi nhưng không có cách phát hiện lỗi còn lại
  • Prompt chi tiết liệt kê mọi edge case: cải thiện lần đầu nhưng Claude vẫn không biết output có chạy được không
Q45
  • Cho Claude truy cập thẳng hệ thống phía sau: bỏ logic, phân quyền, interface có kiểu của server; vẫn không tới được mạng riêng
  • Dùng giao thức agent-to-agent: MCP server là nhà cung cấp tool, không phải agent; không giải quyết khả năng kết nối
  • Dùng MCP connector nối thẳng server stdio: connector chỉ hỗ trợ server public qua HTTP; không có đường mạng tới mạng riêng
Q46

  • Model window lớn hơn, giữ nguyên workflow: chỉ hoãn vấn đề, tăng chi phí, không xử lý context rot
  • Chỉ dẫn agent bỏ qua file đã đọc: không xóa token nào khỏi hội thoại
Q47

  • Cảnh báo khi token tăng đột biến: token đo khối lượng, không đo đúng sai; câu sai tốn token như câu đúng
Q48
  • Lấy key từ remote config lúc khởi động: chỉ đổi cách key tới máy; vẫn trích xuất được từ bộ nhớ
  • Obfuscate key và xoay mỗi release: obfuscate không phải ranh giới bảo mật; mỗi bản cài vẫn có credential tĩnh
  • Giới hạn key vào workspace riêng: giảm phạm vi ảnh hưởng nhưng credential lâu dài vẫn nằm trên mọi thiết bị
Q49
  • Chỉ báo cáo khi trượt mục tiêu: im lặng lâu làm lòng tin xói mòn, kỳ vọng trôi dạt

Q50
  • Lặp lại toàn bộ rule cuối mỗi user message: phình mọi request, không xử lý lý do rule bị áp sai; rule đã rõ vị trí
  • Chuyển rule sang user message đầu tiên: system prompt mới là nơi dành cho rule operator; chuyển đi không ràng buộc hơn
  • Chuyển sang tier mạnh nhất: model mạnh vẫn thiếu lý do để khái quát; nên tinh chỉnh prompt trước
Q51

  • Cắt mạnh max output cho mọi request: cắt cụt câu trả lời cần dài, giảm chất lượng
Q52

  • Chính sách cấm đổi kiến trúc khi chưa duyệt: quy định cách duyệt, không truyền đạt lý do; ép bằng quyền gây bất mãn
  • Buổi walkthrough mỗi khi có người mới hỏi: phụ thuộc kiến trúc sư mãi, không để lại tài liệu bền vững
Q53

  • Dừng và revert vì coi là nhiễu: vội như ship; một ngày là chưa kết luận được theo cả hai hướng
  • Mở rộng thay đổi để hiệu ứng lớn hơn: làm hỏng phép so sánh, kết quả không quy được cho bản sửa ban đầu
Q54

  • Đóng băng prompt và cấu hình model: trái mục đích cải tiến; so sánh được nhờ versioning và chạy lại eval
Q55

  • Giao phân tích cho subagent báo lại trong turn: kết quả về model điều phối, không về người duyệt

  • Bật prompt caching: giảm chi phí gửi lại nội dung, không đổi khối lượng việc trong một lượt

  • Dựa vào kết quả batch tự hết hạn: lưu rồi hết hạn vẫn là đã lưu, đúng điều nghĩa vụ cấm

  • Đặt temperature về 0: không đổi grounding; vẫn bịa cùng giá trị một cách tất định
  • Nâng lên tier mạnh nhất: chẩn đoán sai; model mạnh vẫn bịa khi không được phép báo thiếu dữ liệu

  • Thêm few-shot suy luận đúng: prompt đã được tinh chỉnh kỹ; tiếp tục là phí chu kỳ quanh trần năng lực
