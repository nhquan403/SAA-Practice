1. IAM, kiểm soát truy cập & nhiều tài khoản

  • Cần short-lived credentials để đăng nhập MySQL trên RDS: tạo MySQL user với IDENTIFIED WITH AWSAuthenticationPlugin AS 'RDS' — tên account CSDL phải trùng tên IAM user/role. Không thể cấu hình MySQL dùng thẳng AWS STS, và lệnh AUTH là của Redis chứ không phải RDS. Q1
  • Cấp quyền cho EC2 truy cập S3 an toàn nhất: IAM role gắn vào instance profile với least privilege — không lưu access key trên instance, không tạo IAM user riêng cho ứng dụng, và bucket ACL không nhận EC2 instance ID làm grantee. Q29
  • Giới hạn bucket S3 chỉ cho account trong AWS Organizations, ít effort nhất: thêm điều kiện aws:PrincipalOrgID vào bucket policy — tự cập nhật khi tổ chức thêm/bớt account, không cần liệt kê từng account ID. aws:PrincipalOrgPaths chỉ dùng khi cần giới hạn theo OU cụ thể chứ không phải toàn bộ Organization; SCP chỉ áp dụng được cho account đã ở trong Organizations nên không chặn được account ngoài org. Q14, Q34
  • Xác thực nhiều AWS account bằng corporate directory tập trung: (2 đáp án) tạo AWS Organizations (bật mọi tính năng) rồi tạo account thành viên, và deploy AWS Directory Service tích hợp Active Directory công ty rồi dùng AWS Identity Center để SSO. Amazon Cognito Identity Pool sai vì nó cấp quyền truy cập tài nguyên AWS chứ không xác thực người dùng doanh nghiệp. Q42
  • Chia sẻ lợi ích một Reserved Instance chưa dùng hết sang account khác: (2 đáp án) bật RI sharing trong billing preferences của chính account đã mua RI (không phải management account), và lập AWS Organizations rồi mời các account khác tham gia. AWS RAM không áp dụng cho Reserved Instances (chỉ dùng cho subnet, transit gateway...). Q45

2. Mạng VPC & kết nối

  • Outbound-only internet cho instance ở private subnet: NAT gateway đặt ở public subnet, route table private subnet trỏ qua NAT, và Internet Gateway phải gắn vào VPC (không gắn IGW vào subnet). Không có cách nào kết nối inbound trực tiếp vào private subnet từ internet. Q2
  • Routing transitive giữa nhiều VPC/account, kiến trúc đơn giản: AWS Transit Gateway + chia sẻ qua AWS Resource Access Manager (RAM). VPC peering không hỗ trợ transitive routing dù có bao nhiêu connection. Q5
  • Giới hạn DB chỉ nhận traffic từ application layer: Security Group của DB thêm inbound rule reference tới Security Group của app layer — SG luôn stateful và chỉ có rule allow, không có deny rule (muốn deny theo CIDR phải dùng NACL). Route table hay VPC peering không phải công cụ đúng cho việc lọc theo layer này. Q25
  • Inspect toàn bộ traffic bằng virtual firewall appliance của bên thứ ba trước khi tới web server, ít operational overhead nhất: Gateway Load Balancer trong VPC kiểm tra, cộng GWLB endpoint ở inspection VPC để nhận và chuyển gói tin cho appliance. NLB/ALB không dùng cho packet inspection (chỉ hoạt động Layer 4/7 định tuyến thường); Transit Gateway chỉ định tuyến, không inspect gói tin. Q26
  • Cần kết nối private IP nhanh tới on-premises ngay sau khi migrate ứng dụng: cấu hình Virtual Private Gateway để dựng site-to-site VPN — nhanh hơn nhiều so với Direct Connect (mất nhiều thời gian provision). CloudFront là CDN, không liên quan; Transit Gateway dùng khi cần hub trung tâm cho nhiều VPC/mạng, không phải yêu cầu ở đây. Q28
  • Hai VPC ở hai Region khác nhau (us-west-2 và eu-central-1) cần liên lạc riêng tư: VPC peering + cập nhật route table, và inbound rule trong Security Group của DB (ở Region nhận) phải cho phép theo IP address của app server — không thể reference Security Group ID khác Region, kể cả khi dùng Transit Gateway peering. Q40

3. Lưu trữ: khối, file dùng chung & object

  • Block storage cho EC2, cần mã hóa at-rest + backup volume-level tự động: dùng Amazon EBS đã mã hóa (instance store bị loại vì non-persistent; EFS/S3 không phải block storage) kết hợp Data Lifecycle Manager để tự động hóa snapshot. Q4
  • Clone dữ liệu production sang test cùng Region, hiệu năng I/O cao ngay lập tức: snapshot EBS rồi bật EBS fast snapshot restore (FSR) trước khi restore thành volume mới — loại bỏ độ trễ "first touch" khi đọc block lần đầu nên volume mới có ngay full provisioned performance. EBS Multi-Attach chỉ share volume trong cùng một AZ nên không giúp tạo bản sao độc lập ở môi trường test. Q32
  • Ứng dụng lưu blob 6 MB/document trong Oracle RDS làm database phình to, giảm hiệu năng và tăng chi phí lưu trữ: chuyển các blob ra Amazon S3, chỉ giữ metadata trong DB (mẫu bài toán Write-Once-Read-Many kinh điển). Tăng size instance/storage RDS chỉ tốn thêm tiền chứ không giải quyết gốc vấn đề; DynamoDB đắt hơn S3 cho use case lưu blob. Q58

Bốn kịch bản FSx & khi nào dùng EFS thay vì FSx

  • FSx for Windows File Server (SMB): dùng khi workload là .NET/SQL Server cần shared filesystem Multi-AZ, throughput/IOPS cao Q16; hỗ trợ SMB client on-premises mount cùng filesystem với EC2 trong VPC qua Direct Connect có sẵn Q36; hỗ trợ Distributed File System Namespaces (DFSN) khi migrate shared Microsoft filesystem, với AWS DataSync tự động hóa việc copy dữ liệu sang FSx Q11, Q8.
  • Amazon EFS: NFS, chỉ cho Linux — cần mount target ở mỗi Availability Zone khi muốn shared storage strong-consistency cho Auto Scaling group đa AZ Q56, Q59; hỗ trợ replication cross-region qua AWS Backup với RPO khoảng 15 phút cho hầu hết filesystem, toàn bộ traffic đi trên AWS global backbone — nếu đề đòi resilient shared filesystem có thể restore sang Region khác thì EFS Standard là lựa chọn đúng, không phải FSx for Windows hay FSx for NetApp ONTAP (những dịch vụ này không hỗ trợ cross-region replication kiểu này). Q43

4. Serverless & tích hợp ứng dụng

  • Migrate API on-premises, cần highly available + scalable + cost-effective: Amazon API Gateway làm frontend cộng AWS Lambda làm backend — EC2 với Auto Scaling/ALB kém cost-effective hơn và khó load balance API; CloudFront chỉ đứng trước API Gateway chứ không phải nơi để migrate API tới. Q3
  • Xử lý log file tới 1 GB, ~40 giây/file, tần suất biến động, cần cách cost-effective nhất: S3 event notification gọi trực tiếp AWS Lambda. Đưa qua SQS trước là thừa vì SQS giới hạn message 256 KB nên vẫn phải lưu file thật trong S3 — dùng event notification thẳng từ S3 đơn giản hơn; không dùng event notification để trigger Amazon ECS task. Q10
  • Ứng dụng Aurora + API Gateway + Lambda chậm khi traffic tăng đột biến, cần cải thiện scalability với ít cấu hình nhất: tách 2 Lambda function (nhận dữ liệu / ghi vào DB) qua Amazon SQS queue ở giữa — queue giúp decouple, giảm khả năng mất dữ liệu hoặc outage khi lượng request tăng vọt. Amazon SNS sai vì SNS dùng cho fan-out broadcast, không phải hàng đợi xử lý tuần tự; không thể chạy code Lambda trên EC2 Tomcat. Q22
  • Rollout thay đổi lớn cho API mà giảm rủi ro cho user hiện tại, có theo dõi trước khi full rollout: API Gateway canary release deployment — đưa % nhỏ traffic sang version mới, xác nhận ổn định rồi mới promote canary stage lên production stage. Dùng Route 53 để dịch chuyển DNS dần chậm và phức tạp hơn, DNS propagation cũng không đảm bảo tức thời. Q44
  • Cấp URL riêng và bảo mật cho từng travel agent dưới cùng một domain, ít operational complexity nhất: (3 đáp án) đăng ký domain, tạo wildcard custom domain trong Route 53 hosted zone trỏ về API Gateway; request wildcard ACM certificate cùng Region với API Gateway REST API (regional endpoint bắt buộc cert cùng Region); và tạo custom domain name trong API Gateway, import chính certificate đó. Request certificate ở Region khác chỉ tăng độ phức tạp không cần thiết; tạo hosted zone hoặc API endpoint riêng cho từng agent làm tăng effort quản lý đáng kể. Q54
  • Expose một Lambda function cho bên thứ ba gọi vào qua webhook, ít complexity nhất: API Gateway endpoint trỏ thẳng vào Lambda. SNS topic ARN hay SQS queue ARN không thể được bên ngoài internet invoke trực tiếp; Network Load Balancer không trigger được Lambda (chỉ Application Load Balancer mới trigger được, và vẫn thêm phức tạp không cần thiết). Q55

5. Container & Kubernetes

  • Ứng dụng containerized trên EC2 kết nối PostgreSQL trên EC2 riêng, cần tối ưu operational efficiency và performance: (2 đáp án) migrate PostgreSQL sang Amazon Aurora (tương thích PostgreSQL, có thể đạt throughput tới gấp 3 lần PostgreSQL gốc mà không cần đổi code) và migrate web app sang AWS Fargate với Amazon ECS (serverless, giảm mạnh operational overhead so với tự quản lý container platform). Gộp app và DB vào chung instance chỉ giảm chi phí chứ không cải thiện gì khác; CloudFront/ElastiCache không giải quyết bài toán operational overhead ở đây. Q15
  • Batch job cuối ngày, stateless, có thể re-trigger khi lỗi, cần giảm chi phí và operational overhead: Spot Instances (rẻ hơn On-Demand 70-90%) trong Amazon EKS managed node group (EKS managed node group giảm ops so với tự quản Auto Scaling group EC2 thuần). Q30
  • EKS control plane bật private access, tắt public access, node ở private subnet nhưng không join được cluster: tạo VPC endpoint cho Amazon EKS và Amazon ECR để node giao tiếp control plane và pull container image mà không cần ra internet. Sửa IAM role không giải quyết vấn đề kết nối mạng; VPC peering hay chuyển node sang public subnet đều sai hướng (và vi phạm chính yêu cầu bảo mật ban đầu). Q38
  • Mã hóa Kubernetes ConfigMaps & Secrets tại rest trong EKS: tạo AWS KMS key mới rồi bật EKS KMS secrets encryption trên cluster (envelope encryption cho Secrets lưu trong etcd). AWS Secrets Manager không trực tiếp mã hóa dữ liệu trong etcd; EFS CSI driver chỉ để mount filesystem, không liên quan tới mã hóa secrets. Q52

6. Cơ sở dữ liệu, cache & Aurora

  • Thay thế in-memory caching layer multi-threaded cho database on-premises: Amazon ElastiCache Memcached — engine Memcached hỗ trợ nhiều core/thread và node lớn, trong khi Redis không hỗ trợ multiple CPU cores hay threads. DynamoDB DAX chỉ dùng riêng cho DynamoDB, không phải cache đứng trước database khác. Q9
  • Migrate MySQL on-premises lên AWS, cần HA + cải thiện hiệu năng + offload reporting workload, ít operationally efficient nhất phải cao: Amazon Aurora MySQL-compatible + hướng reporting sang Aurora Replica (Aurora hỗ trợ tới 15 Aurora Replicas chia sẻ cùng storage volume với primary instance). RDS MySQL Single-AZ với read replica cùng AZ không đạt HA; tự quản MySQL trên EC2 tốn ops cao nhất trong các lựa chọn. Q48
  • Multi-tier app chạy 3 Availability Zone, cần scale cho traffic tăng đột biến và giữ HA cho DB lẫn session/cache: Amazon RDS PostgreSQL Multi-AZ + ElastiCache for Redis (replication group quản lý session data và cache reads — Redis có durability/atomicity mà Memcached không có) + Auto Scaling group trải 3 AZ cho app server. Aurora single-AZ hay giữ DB tự quản trên EC2 đều không đạt yêu cầu HA đa AZ của đề. Q51
  • Tự quản MySQL trên EC2, cần co giãn compute lên/xuống theo nhu cầu và cải thiện hiệu năng/scaling/durability với ít effort vận hành nhất: Amazon Aurora Serverless (Aurora MySQL) — tự động scale compute, có sẵn built-in security, continuous backup, up to 15 read replicas, automated multi-Region replication. Đổi sang Aurora PostgreSQL đòi thay đổi schema tương thích; tự dựng EC2 Auto Scaling group cho DB tier vẫn cần quản lý nặng. Q62
  • Mã hóa một RDS database đang chạy và chưa mã hóa, áp dụng cho cả dữ liệu cũ lẫn mới: không thể bật encryption trực tiếp trên instance đang tồn tại, và không thể tạo encrypted read replica từ instance chưa mã hóa — phải snapshot -> tạo bản copy snapshot đã mã hóa -> restore instance mới từ snapshot mã hóa đó, rồi chuyển kết nối ứng dụng sang instance mới. Q64

7. Disaster recovery

  • DR chạy một bản scaled-down nhưng luôn hoạt động, cần giảm recovery time: chiến lược Warm standby — mở rộng từ pilot light bằng cách luôn chạy sẵn hệ thống thu nhỏ của các thành phần business-critical. Backup and restore rẻ nhất nhưng RTO dài nhất; Multi-site chạy song song active-active cả on-premises lẫn AWS, tốn kém hơn nhiều so với yêu cầu đề bài. Q6
  • DR cross-region cho ứng dụng EC2 với RTO ≤ 4 giờ, dùng ít resource nhất khi vận hành bình thường, cost-effective nhất: copy AMI sang secondary Region, dùng AWS CloudFormation để tự động dựng lại hạ tầng khi cần recovery (chỉ site active mới có instance chạy thật nên rẻ nhất). Tự viết Lambda + custom script khó bảo trì hơn CloudFormation cho việc deploy hạ tầng; giữ instance chạy sẵn liên tục ở region/AZ phụ không cost-effective. Q12
  • VM PostgreSQL on-premises cần DR với RPO < 1 phút và RTO ≤ 2 giờ, chi phí thấp nhất: warm standby Amazon RDS for PostgreSQL + AWS DMS dùng change data capture (CDC) để replicate gần real-time từ on-premises, promote standby thành primary khi có sự cố. Active-active multi-site với third-party HA solution đắt và phức tạp hơn hẳn; AWS Elastic Disaster Recovery làm pilot light phù hợp cho server/app chung hơn là chuyên biệt cho database; backup hàng ngày bằng third-party software qua S3 không đạt RPO dưới 1 phút (có thể mất dữ liệu tới 24 giờ). Q49

8. Giám sát, ghi log & dữ liệu nhạy cảm

  • Cần track configuration changes và lịch sử API call chi tiết (ai đăng nhập, gọi API gì, request/response nào): AWS Config theo dõi configuration changes (gửi configuration history file mỗi 6 giờ cho mỗi loại resource nó record), còn AWS CloudTrail ghi lại API call kèm identity, thời gian, source IP, request parameters và response elements. Amazon CloudWatch không theo dõi configuration changes hay API call (nó theo dõi performance metrics); Amazon EventBridge/Amazon Macie không phù hợp cho việc tracking song song này. Q13, Q33
  • Stream CloudWatch Logs sang Amazon OpenSearch Service gần real-time với LEAST operational overhead: CloudWatch Logs subscription trỏ thẳng tới OpenSearch — thêm Kinesis Data Firehose hay tự viết Lambda function đều tốn operational overhead hơn vì phải quản lý thêm một service hoặc tự viết/maintain code. Q18
  • So sánh chi phí EC2 hai tháng gần nhất theo instance type, phân tích sâu nguyên nhân vertical scaling, ít overhead nhất: Cost Explorer với granular filtering — dễ truy cập, có sẵn filter và graph theo khoảng thời gian. AWS Budgets chỉ dùng để cảnh báo khi vượt ngưỡng; billing dashboard mặc định không đủ granularity; Cost and Usage Report + QuickSight cho ra kết quả tương tự nhưng operational overhead cao hơn nhiều. Q20
  • Cần alert ngay khi có API call CreateImage cụ thể được gọi, ít operational overhead nhất: Amazon EventBridge rule bắt sự kiện dựa trên CloudTrail API call, target là Amazon SNS topic gửi alert. Viết Lambda tự query CloudTrail logs, dùng Athena, hay đẩy CloudTrail logs vào SQS FIFO queue (vốn không hỗ trợ trực tiếp) đều tốn effort hơn nhiều. Q27
  • Chia sẻ dashboard CloudWatch cho người không có quyền admin trên account (theo nguyên tắc least privilege): dùng tính năng Share Dashboard ngay trong CloudWatch console, nhập email người nhận, gửi link — không cần tạo IAM user/credentials riêng cho mỗi người xem, càng không cần dựng bastion server để mở trình duyệt hộ họ. Q31
  • Tự động phát hiện PHI (protected health information) trong S3 và báo compliance team: Amazon Macie (machine learning phát hiện dữ liệu nhạy cảm) kết hợp Amazon EventBridge rule lọc theo loại Macie finding rồi kích hoạt thông báo (ví dụ qua Amazon SES) tới compliance team. AWS Security Hub không phát hiện được loại dữ liệu cụ thể (PHI) nằm trong S3 object nên không đáp ứng yêu cầu đề bài. Q53
  • Phân tích lỗi Access Denied/Unauthorized từ CloudTrail logs với LEAST effort: Amazon QuickSight kết nối trực tiếp tới S3 bucket nơi CloudTrail lưu log rồi dựng dashboard trực quan. Viết custom script chạy trên AWS Batch hoặc AWS Glue, hay dùng Amazon RedShift, đều tốn effort thiết lập và duy trì hơn nhiều. Q60

9. WAF, Shield & Firewall Manager

  • Bảo vệ serverless API (API Gateway) ở 2 Region khỏi SQL injection và cross-site scripting, ít administrative effort nhất: AWS Firewall Manager cấu hình tập trung AWS WAF rules áp dụng cho cả hai Region cùng lúc, tự động áp dụng khi thêm account/resource mới về sau. Tự set WAF riêng lẻ từng Region tốn effort quản lý rule hơn hẳn; AWS Shield chỉ chống DDoS ở Layer 3/4 của mô hình OSI, không chống được SQL injection/XSS ở Layer 7. Q21
  • Web layer có nguy cơ bị tấn công cross-site scripting (XSS): dựng Application Load Balancer rồi bật AWS WAF trên đó — AWS WAF chỉ gắn được vào ALB, không gắn được vào Classic Load Balancer hay Network Load Balancer. AWS Shield Standard chỉ chống DDoS, không chống được XSS. Q57

10. CloudFront: bảo mật & tăng tốc nội dung

  • Ứng dụng 3 tầng (EC2 + ALB + DynamoDB) chậm khi tải cao, cần cải thiện mà không rearchitect: (2 đáp án) đặt Amazon CloudFront trước ALB để cache content ở edge location toàn cầu, và thêm DynamoDB Accelerator (DAX) làm cache trước DynamoDB table. Chuyển DynamoDB sang Aurora hay chuyển web app sang AWS Fargate đều là rearchitect thật sự — vi phạm đúng ràng buộc "không rearchitect" của đề bài. Q35
  • Chỉ học viên đã đăng ký mới xem được tài liệu khóa học trên CloudFront/S3, kèm việc thỉnh thoảng cấp quyền cho nhiều file/thư mục cùng lúc cho một số học viên nhất định: CloudFront signed cookies — một cookie áp dụng được cho nhiều file trong một hoặc nhiều thư mục, khác S3 pre-signed URL vốn chỉ cấp quyền cho từng object riêng lẻ (kém hiệu quả hơn khi cần cấp quyền hàng loạt). S3 object-level encryption chỉ bảo vệ dữ liệu at-rest chứ không kiểm soát ai được truy cập; CloudFront Field-Level Encryption dùng để bảo vệ dữ liệu nhạy cảm trong HTTP POST request, không phải để chặn truy cập nội dung. Q46
  • Phát hành nội dung dần theo từng khu vực, phải chặn hẳn người dùng ở khu vực chưa được release: CloudFront geographic restriction dùng deny list kèm custom error message. Signed URL/cookie hay mã hóa dữ liệu đều không quan tâm tới vị trí địa lý người xem nên không đáp ứng đúng yêu cầu. Q50

11. Dữ liệu lớn, streaming & truy vấn

  • Ảnh upload lên S3 -> phân tích demographic -> lưu .CSV ở bucket khác, cần mã hóa at-rest và query bằng SQL, giải pháp fully serverless: S3 với AWS KMS encryption + Amazon Athena để query (Athena serverless, hỗ trợ dữ liệu và kết quả query đã mã hóa qua KMS). Amazon RedShift Spectrum cần cluster RedShift chạy nền EC2 nên không serverless; Amazon Managed Service for Apache Flink dùng cho streaming data trong Kinesis chứ không phải file tĩnh trên S3; QuickSight là dashboard trực quan, không phải công cụ chạy truy vấn. Q7
  • Reporting/visualize dữ liệu từ cả Amazon S3 lẫn Amazon RDS PostgreSQL trong cùng data lake, chỉ management team được full access, số còn lại hạn chế: Amazon QuickSight kết nối cả hai nguồn, publish dashboard, rồi share theo users và groups (chi tiết và phù hợp hơn IAM role cho việc phân quyền xem dashboard). AWS Glue + Athena Federated Query ra được số liệu tổng hợp nhưng thiếu khả năng visualization/dashboard theo yêu cầu đề bài. Q19
  • Call center cần nhận diện nhiều speaker trong cùng cuộc gọi, sinh transcript, rồi query transcript bằng SQL để phân tích pattern: Amazon Transcribe (chuyển audio sang text, hỗ trợ multiple speaker recognition) + Amazon Athena (SQL trực tiếp trên S3, serverless). Amazon Rekognition dùng cho ảnh/video (object, scene, face), không xử lý audio; Amazon Translate chỉ dùng để dịch ngôn ngữ. Q23
  • Thiết bị edge sinh ~1 TB alert/ngày, mỗi entry ~2 KB, cần highly available, không muốn quản thêm infrastructure, giữ 14 ngày để phân tích rồi archive phần cũ hơn: Amazon Kinesis Data Firehose ingest rồi deliver thẳng vào Amazon S3 bucket, cộng S3 Lifecycle configuration chuyển data sang S3 Glacier sau 14 ngày (Firehose tự load thẳng tới đích, không cần hạ tầng trung gian). Thêm fleet EC2 + ALB nghĩa là phải provision thêm infrastructure — trái yêu cầu; đẩy vào OpenSearch rồi manual snapshot + xóa dữ liệu cũ hơn 14 ngày là xóa chứ không phải archive; dùng SQS standard queue buộc phải tự viết consumer poll và kiểm tra tuổi message, tức vẫn phải quản thêm hạ tầng xử lý. Q24
  • Dữ liệu shipment cập nhật mỗi vài giây, cần real-time analysis để dự đoán delay rồi đổ vào S3-based data lake, ưu tiên operational efficiency nhất: Amazon Kinesis Data Firehose ingest tốc độ cao (capture/transform/load thẳng vào S3) kết hợp Amazon Managed Service for Apache Flink để phân tích streaming real-time. Kinesis Data Streams + Lambda vẫn phải tự quản lý và scale stream consumer; AWS Direct Connect không phải công cụ ingest dữ liệu tốc độ cao; Amazon SQS + Amazon EMR không phù hợp cho phân tích real-time. Q41

12. Di trú dữ liệu lớn: Snow Family & AWS Glue

  • 45 TB dữ liệu cần chuyển vào cloud, đường truyền internet đã saturated, công ty chấp nhận pause ứng dụng transform hàng tuần và muốn bắt đầu transfer càng sớm càng tốt, transform job phải tiếp tục chạy được trên cloud, ít operational overhead nhất: order 1 AWS Snowball Edge Storage Optimized device để copy dữ liệu vật lý (mạng đã saturated nên AWS DataSync — vốn là dịch vụ transfer online — không khả thi), rồi tạo transformation job bằng AWS Glue (managed service, ít vận hành hơn tự chạy job trên EC2 instance như phương án Snowball Edge kèm compute). Q61
  • 500 TB dữ liệu, băng thông internet thấp, phải hoàn tất trong vài tuần, cần giải pháp MOST cost-effective: 7 AWS Snowball appliances (mỗi Snowball Edge chứa được tới 80 TB, nên 500 TB ÷ 80 TB ≈ 7 thiết bị) chọn Amazon S3 bucket làm đích (Snowball không thể chọn thẳng một S3 Glacier vault làm đích), sau đó dùng S3 Lifecycle policy để chuyển các object sang S3 Glacier. AWS Direct Connect mất nhiều thời gian setup và không cost-effective bằng; AWS Global Accelerator không tăng tốc upload từ mạng on-premises băng thông thấp. Q65

13. Tối ưu vận hành & chi phí compute

  • Patch/update phần mềm bên thứ ba khẩn cấp cho hàng nghìn EC2 instance, cần vá càng nhanh càng tốt để remediate lỗ hổng bảo mật: AWS Systems Manager Patch Manager — được thiết kế sẵn để scan/patch instance theo tag hàng loạt, nhanh và có sẵn (không cần custom code). Maintenance Windows chỉ phù hợp khi cần patch trong một khung giờ cố định, không phải "ngay lập tức"; tự viết Lambda function để config và validate lại patch tốn effort code hơn hẳn. Q17
  • Cần cài đặt một công cụ tùy ý (không phải patch định kỳ) trên 500 EC2 instance nhanh và hiệu quả nhất, việc này còn lặp lại về sau và phải scale khi thêm instance mới: AWS Systems Manager Run Command — chạy cùng một command trên nhóm lớn instance mà không cần SSH riêng lẻ vào từng máy hay quản access key. Q37
  • Đảm bảo mọi AWS resource — kể cả resource chưa được gắn tag — đều được backup đầy đủ, ít operational overhead nhất: AWS Config tự động phát hiện resource thiếu tag và gắn tag theo chương trình, kết hợp AWS Backup tự động backup theo tag (trung tâm hóa qua policy, quản lý qua một dashboard). Tự tìm thủ công hoặc để từng account owner tự lo đều thiếu nhất quán và tốn effort hơn nhiều; tự viết Lambda quét định kỳ vẫn phải code và maintain script riêng thay vì dùng sẵn AWS Config. Q39
  • Auto Scaling group co giãn từ 2 lên tới 20 instance theo giờ hành chính, nhưng ứng dụng chậm hẳn vào đầu giờ sáng dù chạy tốt vào giữa buổi — cần vừa khắc phục hiệu năng vừa giữ chi phí thấp nhất: target tracking scaling policy với ngưỡng CPU thấp hơn hiện tại, cộng giảm cooldown period — scale ra trước khi CPU chạm ngưỡng ảnh hưởng hiệu năng, đồng thời terminate instance thừa nhanh hơn để tiết kiệm chi phí. Scheduled action đặt desired/min-max = 20 trước giờ mở cửa vẫn giữ nguyên 20 instance chạy suốt cả ngày dù nhu cầu thực tế thấp hơn — không cost-effective; AWS khuyến nghị dùng target tracking thay vì step scaling cho hầu hết trường hợp. Q63

14. Case study: nền tảng game serverless

Câu hỏi 3-đáp-án đúng Q47 gói gọn một pattern kiến trúc serverless đầy đủ cho ứng dụng có traffic khó đoán, đáng nhớ nguyên khối:

  • Compute + dữ liệu: AWS Lambda đọc player info từ Amazon DynamoDB, phía trước là Amazon API Gateway làm REST endpoint gọi Lambda — mô hình pay-per-use này hợp với traffic không đoán trước được, có lúc idle kéo dài hơn hẳn so với chạy Amazon ECS đứng sau Application Load Balancer (vốn luôn cần capacity sẵn sàng, tốn kém hơn khi idle).
  • Xác thực người dùng: Amazon Cognito User Pools xử lý sign-up/sign-in để đảm bảo chỉ người đã mua game mới login được — khác hẳn Cognito Identity Pools, vốn chỉ dùng để cấp quyền truy cập tài nguyên AWS chứ không xác thực người dùng.
  • Frontend: AWS Amplify host giao diện HTML/CSS/JS với tích hợp sẵn cấu hình Amazon CloudFront để phân phối toàn cầu — triển khai tự động hơn so với tự dựng riêng S3 static website hosting rồi tự cấu hình CloudFront.

17. Mẹo làm bài thi

  • Đọc câu hỏi cuối trước, rồi mới đọc tình huống. Xác định ngay đề đang hỏi "LEAST operational overhead", "MOST cost-effective" hay "LEAST amount of effort" sẽ giúp loại nhanh các đáp án đúng về mặt kỹ thuật nhưng thừa công sức vận hành.
  • "Fully managed"/"least operational overhead" luôn đẩy về dịch vụ càng tự động càng tốt. Aurora Serverless hơn Aurora, Aurora hơn RDS, RDS hơn tự quản database trên EC2; Fargate hơn EC2 thuần cho container; managed rule/policy (Config, Backup, Systems Manager) hơn tự viết Lambda script.
  • Phân biệt CloudTrail và AWS Config theo đúng chiều. CloudTrail trả lời "ai đã gọi API gì, khi nào, từ IP nào"; AWS Config trả lời "resource đang được cấu hình ra sao, có đổi so với trước không". Nhầm chiều là sai ngay lập tức. Q13, Q33
  • "Select TWO/THREE" phần lớn là các bước bổ trợ của cùng một giải pháp, không phải lựa chọn độc lập. Q15 (Aurora + Fargate), Q35 (CloudFront + DAX), Q42 (Organizations + Directory Service), Q45 (bật RI sharing + tạo Organizations), Q47 (Lambda + Cognito User Pools + Amplify), Q54 (domain + certificate + custom domain API Gateway) đều là những mảnh ghép cần cả hai/ba mới trọn vẹn giải pháp.
  • Custom domain cho API Gateway REST API luôn cần ACM certificate cùng Region. Request certificate ở Region khác là sai ngay, dù về mặt kỹ thuật certificate vẫn tồn tại. Q54
  • Khi đề có DR: định vị RTO/RPO cụ thể trước khi chọn chiến lược. Số càng nhỏ (RPO tính bằng phút, RTO vài giờ) thì chiến lược càng gần active-active/warm standby; số lớn (RPO/RTO tính bằng giờ/ngày) mới cân nhắc backup and restore hay pilot light. Q6, Q12, Q49
  • "Không rearchitect"/"minimal configuration effort" là ràng buộc cứng, không phải gợi ý. Đáp án nghe hay nhưng đổi hẳn loại database hay compute layer (như đổi DynamoDB sang Aurora, hay EC2 sang Fargate khi đề không yêu cầu) đều bị loại ngay cả khi kỹ thuật đúng. Q35

18. Bẫy thường gặp

  • CloudTrail và AWS Config bị hoán đổi vai trò. Đề nào cho "AWS CloudTrail để tract configuration changes, AWS Config để record API calls" là đã đảo ngược — đúng phải là chiều ngược lại. Q13, Q33
  • Cognito Identity Pools bị nhầm dùng để xác thực người dùng. Identity Pools chỉ cấp quyền truy cập tài nguyên AWS (temporary AWS credentials); xác thực người dùng cuối (sign-up/sign-in) phải là Cognito User Pools. Q42, Q47
  • Security Group reference chỉ hoạt động trong cùng một Region. Muốn cho phép traffic từ app server ở Region khác vào DB, phải dùng inbound rule theo dải IP address, không thể reference Security Group ID của Region khác — kể cả khi nối qua Transit Gateway peering. Q40
  • Amazon FSx for Windows File Server không hỗ trợ cross-region replication. Cần shared filesystem có thể khôi phục sang Region khác thì phải chọn Amazon EFS Standard, không phải các biến thể FSx. Q43
  • Amazon EFS chỉ dùng được cho NFS/Linux. Nghe "shared file system" chung chung rất dễ chọn nhầm EFS cho workload Windows/SMB — trường hợp đó luôn phải là FSx for Windows File Server. Q16, Q36
  • AWS Snowball chỉ chọn được Amazon S3 bucket làm đích, không thể chọn thẳng một S3 Glacier vault. Muốn dữ liệu vào Glacier vẫn phải đổ vào S3 bucket trước rồi dùng Lifecycle policy chuyển tiếp. Q65
  • Không có cách bật encryption trực tiếp trên một RDS instance đang chạy, cũng không tạo được encrypted read replica từ instance chưa mã hóa. Luôn phải đi qua vòng snapshot -> copy mã hóa -> restore. Q64
  • AWS WAF chỉ gắn được vào Application Load Balancer. Đề nào đưa phương án Classic Load Balancer hay Network Load Balancer kèm "enable AWS WAF" là sai kỹ thuật ngay, không cần xét tiếp yêu cầu khác của đề. Q57
  • AWS Shield chỉ chống DDoS (Layer 3/4), không chống SQL injection/XSS (Layer 7). Vai trò chống tấn công ứng dụng web luôn thuộc về AWS WAF, không phải Shield (kể cả Shield Advanced). Q21, Q57
  • Amazon Athena và Amazon QuickSight không phải công cụ ETL/transform. Khi đề yêu cầu một "custom transformation job" thực thụ chạy trên cloud, dịch vụ đúng là AWS Glue, không phải chỉ dừng ở việc query hay visualize dữ liệu. Q61
