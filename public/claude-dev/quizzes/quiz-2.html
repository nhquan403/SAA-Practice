1. Messages API, streaming & xử lý lỗi

  • Streaming: SSE, text tới qua content_block_delta → dấu hiệu đề "hiện từng chữ", "tưởng app treo" Q1
  • Thứ tự sự kiện: message_start → content block → message_delta (stop_reason, usage cộng dồn) → message_stop; hoặc lấy final Message của SDK Q9
  • HTTP 200 ≠ stream thành công: lỗi giữa chừng là error event (overloaded_error); giữ text dở, gửi continuation request (4.6+) Q1, Q33
  • 429 rate_limit_error: tạm thời; để SDK retry backoff + retry-after, traffic tăng vọt thì tăng dần → "50 → 2.000 request/phút" Q13
  • Python SDK: tự retry 2 lần rồi ném exception có kiểu; PR đêm cần model/prompt cấu hình được, xử lý lỗi, integration check Q38
  • Async service: client đồng bộ chặn event loop → dùng AsyncAnthropic + await → dấu hiệu đề "health check timeout" Q49
  • API stateless: project instructions claude.ai không theo sang API; đưa chỉ dẫn vào system rồi test lại Q27, Q32
  • Kết quả không nhất quán: ghi trace đầy đủ + request_id, so lần tốt với lần lệch trước khi đổi model/temperature Q13, Q37

2. Token, context window, prompt caching & Files API

  • Context window chung input + output: ngân sách = input + max_tokens + tool result sau; đếm bằng token counting endpoint; vượt là lỗi, không tự cắt Q2
  • Tool definitions: là input token, kèm tool-use system prompt cố định → dấu hiệu đề "input_tokens tăng khi thêm tools" Q45
  • Task budget ≠ max_tokens: budget advisory cho cả vòng agentic; quá nhỏ gây dừng sớm/thu hẹp → tăng budget, đo token thực Q5
  • Prompt caching: tái dùng prefix không đổi; hit rẻ, write đắt hơn chút, TTL 5 phút; hợp hội thoại nhiều lượt Q28
  • Files API: upload một lần, dùng file_id; mỗi tài liệu một document block có title → dấu hiệu đề "gán nhầm nguồn" Q8
  • Tài liệu dùng hàng nghìn lần: Files API + block đầu request + cache; phần thay đổi đặt sau Q48
  • Context pollution: context lớn giảm recall; cắt tỉa/tóm tắt tool result cũ, giữ yêu cầu và quyết định đang mở Q17, Q22, Q47

3. Prompt engineering & tham số model

  • Nói làm gì ≠ cấm làm gì: yêu cầu văn xuôi thay "Do not use markdown"; prompt viết bullet kéo output thành markdown Q7
  • Prefill: không còn hỗ trợ, trả 400; ép JSON bằng structured outputs Q7, Q40
  • Temperature: 4.7+ từ chối giá trị tùy chỉnh (400); chỉ đổi độ đa dạng, không đổi độ cẩn thận Q22, Q37, Q40
  • Hụt suy luận nhiều bước: adaptive thinking + effort cao cho route khó, chạy lại bộ nhãn Q22
  • Prompt phình to: audit rồi viết lại, bỏ trùng/mâu thuẫn; context là ngân sách chú ý hữu hạn Q36
  • System prompt: chỉ dẫn bền vững cấp operator, version cùng code Q27
  • Migration model: theo migration guide, bỏ prefill/sampling, đếm lại token, chạy lại eval; không gộp đổi schema Q40

4. Tool use & structured output

  • Mô tả tool chi tiết: yếu tố quan trọng nhất; tên rõ hành động, nói khi nào dùng → dấu hiệu đề "lookup2, gọi nhầm tool" Q6
  • Thứ tự history: assistant turn có tool_use nguyên văn → tool_result với tool_use_id khớp Q21
  • Schema là hợp đồng: đúng kiểu + strict: true; không hỗ trợ minimum nên kiểm "≥ 1" trong executor Q35
  • Hình dạng ≠ giá trị đúng: kiểm stop_reason (refusal, max_tokens), validate schema, kiểm business rule trước khi dùng Q25, Q41, Q51
  • Ví dụ JSON trong prompt: không đảm bảo; bắt từ khóa văn xuôi mong manh ("not approved") Q41

5. Kiến trúc agent: workflow, routing & subagent

  • Bước cố định ≠ agent: quy trình bắt buộc đúng thứ tự → workflow trong code có gate, tự ghi audit log → dấu hiệu đề "auditor" Q3, Q39
  • Kết hợp: bước bắt buộc tất định; điều tra mở giao agent có giới hạn (tool read-only, turn budget) Q39
  • Parallelization: chỉ cho subtask độc lập; bước phụ thuộc chạy song song là phá thứ tự Q3, Q39
  • Routing: câu dễ sang model rẻ, câu khó sang model mạnh; mỗi route có eval riêng Q15
  • Orchestrator-worker: coordinator phân rã + tổng hợp; subagent có toolset, history riêng Q19
  • Subagent: conversation riêng, chỉ message cuối về parent → giữ context chính nhỏ Q17, Q19
  • Managed Agents ≠ Agent SDK: Managed khi không muốn vận hành hạ tầng; SDK khi nhúng loop vào process mình Q24
  • Agent dài: quản lý nội dung context, không giảm số tool call hay mua window lớn Q47
  • Override SDK cũ: xét từng cái — yêu cầu gốc, SDK đã hỗ trợ chưa, test khi bỏ Q53

6. Agent SDK, MCP, Skills & memory

  • Custom tool trong process: @tool + create_sdk_mcp_server, tên mcp__{server}__{tool}, thêm vào allowed tools Q10
  • Dùng built-in, thêm cái thiếu: sửa file bằng tool built-in + permission; API nội bộ bằng custom tool/MCP hẹp Q16
  • Resource ≠ tool ≠ prompt: resource đọc có URI + subscription; tool hành động cần người duyệt; prompt là template Q26, Q16
  • Skill vs MCP server: Skill đóng gói quy trình, nạp dần; MCP mở thao tác dịch vụ chung; bổ trợ nhau Q46
  • Memory tool: client-side; handler ánh xạ đường dẫn theo từng user để cô lập Q32
  • Approval SDK: allowedTools cho tool read-only; tool nhạy cảm rơi vào canUseTool hỏi người Q20, Q43

7. Claude Code: cấu hình & quy trình làm việc

  • CLAUDE.md + @path ≠ rule có điều kiện: nạp toàn bộ mỗi session; chỉ .claude/rules/ có paths nạp theo file khớp Q12, Q23
  • Settings precedence: local > project > user; managed đứng trên tất cả; xem bằng /status Q52
  • /clear vs /compact: clear cho việc mới (sau /resume được); compact tiếp cùng tác vụ Q30
  • Feature mơ hồ: phỏng vấn bằng AskUserQuestion → SPEC.md → implement ở session mới Q23
  • Thay đổi lớn, nhạy cảm: plan mode, từng bước có giới hạn, mỗi bước commit + test tự chạy Q50
  • Hook: matcher + if thu hẹp; PreToolUse exit code 2 chặn; bỏ hook khỏi lệnh đọc rủi ro thấp Q29
  • Plugin dependency: mặc định bản mới nhất; ghim semver (~2.1.0) trong plugin.json, tag release Q14

8. Bảo mật, guardrail & human-in-the-loop

  • Code ≠ prompt: ranh giới phải tất định trong code; phương án "thêm chỉ dẫn system prompt" thay kiểm soát gần như sai Q4, Q20, Q29, Q39
  • Data minimization: bỏ trường không cần trước khi gửi; phân quyền ở retrieval; khóa pseudonym nằm ngoài hệ thống Q4
  • Least privilege: ngưỡng trong executor, vượt thì người duyệt; xóa file: read-only lập kế hoạch + tool xóa hẹp Q20, Q42
  • Ngăn chặn > phát hiện: version history, review sau, batch đêm không ngăn thiệt hại Q3, Q41, Q42
  • Rollout production: read-only qua allowedTools, deploy qua canUseTool hỏi release manager Q43
  • Prompt injection: input user không tin cậy dù đã đăng nhập; sanitize, tách bằng thẻ, validate output Q51
  • Quyền rộng: shell không giới hạn, credential toàn quyền là sai; tool hẹp dễ audit Q10, Q16, Q20

9. Yêu cầu, đánh giá & vòng đời phát hành

  • Brief mơ hồ: chức năng nêu input/output cụ thể; "nhanh" → latency ở percentile + lưu lượng đỉnh Q11
  • Functional spec ≠ SLO: spec = hệ thống làm gì; SLO = latency, availability; "cảm giác thông minh" không thuộc cả hai Q34
  • Thay prototype: chụp hành vi thành baseline eval set trước, giữ prototype làm rollback Q18
  • Prompt là code: file có version, review, eval trong CI, ghi version mỗi release Q31, Q27
  • Sau release: chấm mẫu production hằng ngày cùng rubric, so baseline; Claude tự chấm không độc lập Q44
  • Mỗi lần một biến: đổi nhiều thứ cùng lúc thì không quy được regression Q18, Q31, Q37, Q40
  • Yêu cầu trước implement: lấy từ stakeholder trước khi chọn model; PR không để "ticket làm sau" Q11, Q38

13. Mẹo làm bài thi

  • Hỏi "ép buộc ở đâu?": đáp án đúng đặt kiểm soát ở code, schema, permission, hook — không ở prompt.
  • Ngăn chặn ≠ phát hiện: đề đòi "trước khi" thì loại review sau, batch đêm, hook chạy sau.
  • Mỗi cơ chế một vấn đề: streaming–thời điểm, schema–hình dạng, caching–chi phí, max_tokens–độ dài.
  • "Select two" là hai lớp bổ trợ: input/output Q51, tự động/người duyệt Q20, chức năng/vận hành Q11, built-in/thêm thiếu Q16, tất định/agent Q39.
  • Đo trước, đổi sau: chọn phương án có eval, baseline, trace; loại đổi model khi chưa có bằng chứng.
  • Nghi "thêm nhiều hơn": context, chỉ dẫn dài hơn hiếm khi đúng; chú ý là hữu hạn.
  • Tham số đã bỏ: prefill, temperature, ép tool_choice trên model mới — kiểm kỹ phương án dựa vào chúng.
  • Ưu tiên thứ có sẵn: SDK retry, final-message helper, built-in tool, Managed Agents.

Học đáp án đúng chỉ giải được đúng câu đó. Hiểu vì sao từng đáp án sai lại sai giúp nhận diện được cả họ câu hỏi tương tự, kể cả khi đề đổi cách hỏi. Mỗi dòng dưới đây là một câu, liệt kê các đáp án sai và lý do sai thật sự — đúc kết từ chính phần giải thích của đề, không phải suy đoán.

CâuĐáp án sai & vì sao sai
Q1
  • Structured JSON output, trả object khi xong: structured output chỉ quy định hình dạng, không quy định lúc nào trả — người dùng vẫn chờ đủ 40 giây
  • Bật prompt caching cho chỉ dẫn lặp lại: caching giảm chi phí và độ trễ của input lặp lại, không biến phản hồi thành luồng sự kiện output
  • Chờ bản non-streaming rồi cắt nhỏ ở client: chỉ giả lập hiệu ứng gõ chữ, người dùng vẫn chờ hết thời gian sinh trước khi thấy gì
Q2
  • Đặt max_tokens bằng cả context window, để API tự cắt input: API không cắt input; input vượt window bị từ chối bằng lỗi
  • Chỉ đếm tài liệu truy xuất: system prompt, 30 lượt history và tool definitions cũng là input token — ngân sách sai ngay từ lượt đầu
  • Coi context window là ngân sách riêng cho output: window dùng chung cho input và output; tính riêng là đếm trùng, request sẽ không vừa
Q3
  • Lưu thứ tự bước trong memory file để Claude tự ghi tiến độ: Claude vẫn tự quyết bước tiếp theo, audit trail chỉ là lời tự khai của model
  • Agent theo thứ tự ghi trong system prompt, agent thứ hai review sau: agent có thể chọn đường khác; review sau chỉ phát hiện khi tài khoản đã đóng, không ngăn chặn
  • Chạy 4 subagent song song: các bước phụ thuộc nhau, chạy song song phá đúng thứ tự mà kiểm toán bắt buộc
Q4

  • Dặn Claude bỏ qua hồ sơ của phòng khám khác: dữ liệu đã bị gửi đi rồi; lọc bằng prompt là xác suất, phân quyền phải tất định
  • Tải hồ sơ mọi phòng khám lên Files API dùng chung: file trên Files API truy cập được toàn workspace, mở rộng quyền thay vì thu hẹp

  • Bỏ max_tokens vì xung đột với task budget: hai giá trị độc lập; max_tokens là trần bắt buộc mỗi request, bỏ đi mất luôn bảo vệ chống sinh vô hạn

  • Bọc parseInt, lỗi thì coi là 0: parseInt("2.5") ra 2 làm sai đơn hàng âm thầm; che lỗi thay vì báo lỗi, hợp đồng vẫn sai

  • Giữ prompt mâu thuẫn, để Claude tự nhận ra quy tắc lỗi thời: Claude không biết quy trình nào đã ngừng; mỗi request có thể giải mâu thuẫn khác nhau
  • Chia thành các phần trong system message: chia phần không làm từng phần nạp riêng, mâu thuẫn vẫn tới cùng request
  • Thêm chỉ dẫn mạnh hơn ở cuối: thêm chữ mà không gỡ mâu thuẫn, dựa vào giả định "quy tắc mới nhất thắng"
Q37
  • Retry ngay và xem lần sau có ra đúng không: không ghi lại context request cần để giải thích lỗi đầu; lần sau đúng có thể che lỗi tích hợp như cắt file đính kèm
  • Đổi sang model mạnh hơn trước khi thu trace: đổi nhiều biến cùng lúc; kết quả tốt hơn không chứng minh nguyên nhân là năng lực model
  • Hạ temperature rồi chạy lại: trên Claude 4.7 trở lên temperature khác mặc định trả lỗi 400; cải thiện sau khi đổi tham số không phải chẩn đoán
Q38
  • Đòi cấu hình và test, hoãn xử lý lỗi API: job chạy đêm trên toàn catalog dễ gặp rate limit; bỏ ngỏ đường lỗi đã biết
  • Đòi model lớn hơn và một demo thành công: model tốt hơn không thêm kiểm soát kỹ thuật nào; một demo không nói gì về đường lỗi
  • Duyệt luôn, tạo ticket làm sau: happy path không kiểm được lỗi API; ticket không thêm hành vi còn thiếu vào code đang review
Q39
  • Một agent tự trị lo cả kiểm tra, điều tra và phê duyệt: thứ tự thành lời dặn có thể không theo; mất điểm quyết định của con người
  • Thay điều tra bằng script cố định truy vấn mọi nguồn: chậm và tốn khi bằng chứng khác nhau theo case; tất định sai chỗ
  • Chạy các giai đoạn bằng agent song song: các giai đoạn phụ thuộc nhau; phê duyệt không thể xảy ra trước khi có bằng chứng
Q40
  • Chỉ đổi model ID, giữ nguyên request: Sonnet 5.5 từ chối prefill và sampling parameter bằng lỗi 400 ngay request đầu tiên
  • Giữ Sonnet 4.5 sau ngày retire: model đã retire ngừng phục vụ request, dịch vụ sẽ ngừng chạy
  • Đổi model và output schema cùng một lần deploy: hai thay đổi một lúc, accuracy giảm không biết do model hay schema
Q41
  • Cho ví dụ JSON trong user message, parse được gì thì gửi: ví dụ không ép format; đẩy phản hồi không parse được xuống downstream là chuyển vấn đề đi
  • Trả lời văn xuôi, downstream bắt từ khóa approved/denied: mong manh — "not approved" vẫn chứa "approved"
  • Ghi thẳng vào record, batch đêm quét lỗi: quyết định sai sửa record hàng giờ; yêu cầu là chặn trước khi cập nhật
Q42
  • Toàn quyền ghi/xóa nhưng chỉ chạy giờ thấp điểm: giờ chạy chỉ đổi ai phát hiện, một lần hiểu sai vẫn xóa mất file đang dùng
  • Nạp danh sách toàn bucket vào context: thêm thông tin không thêm kiểm soát, còn làm chật context và giảm accuracy
  • Toàn quyền xóa, dựa vào version history để khôi phục: khôi phục sau khi xóa thì khách đã mất truy cập; không phải bucket nào cũng có version
Q43
  • Khởi chạy agent thứ hai toàn quyền để deploy: bỏ hẳn bước phê duyệt, rollout chạy với nhiều quyền hơn trước
  • Cấp mọi tool ngay đầu session: rollout chạy không cần phê duyệt, phá yêu cầu cốt lõi
  • Bỏ deploy tool, in lệnh shell để người chạy tay: mất context, log và validation của agent; người có thể chạy nhầm lệnh cũ
Q44
  • Tin kết quả offline, chỉ xem lại khi khiếu nại tăng: khiếu nại là tín hiệu chậm, không phát hiện được trong một ngày
  • Chạy lại bộ offline mỗi giờ: đo lại đúng các case cũ, không bao giờ chạm tới loại câu hỏi ít được phủ; chênh lệch chủ yếu là nhiễu
  • Để Claude tự chấm câu trả lời 1–10: tự chấm là một output khác của model, không độc lập; rollback tự động theo tín hiệu này không đáng tin
Q45
  • Tool definition tính là output token khi được chọn: definition gửi cùng request và tính là input; usage báo đúng
  • Context limit áp riêng từng block, tool tính giá cao hơn: window áp cho cả request; tool definition cùng giá input như mọi input khác
  • Chỉ user message cuối tính input, phần thừa do cache tự thêm: mọi phần request đều tính input; API không tự thêm nội dung cache
Q46
  • Bọc một built-in tool có sẵn: wrapper không tạo phân phối hay hỗ trợ giao thức cho team khác, cũng không đóng gói quy trình
  • Endpoint HTTP không MCP, nhét quy trình vào dữ liệu trả về: client không coi text trả về là Skill đã cài hay MCP tool khám phá được
  • Thư viện dùng chung mỗi team tự import: mỗi ứng dụng vẫn phải tự nối code và giữ version; Skill và MCP đáp ứng trực tiếp hơn
Q47
  • Chọn context window lớn hơn, giữ nguyên mọi kết quả: window còn chỗ, vấn đề là độ liên quan; window cỡ nào cũng bị context pollution
  • Gộp tool thành thao tác đa năng: ít lần gọi hơn nhưng vẫn trả về chừng ấy nội dung thừa, không quyết định cái gì được giữ lại
  • Cache toàn bộ prefix và giữ kết quả cũ: caching giảm chi phí, không loại bỏ kết quả thừa hay làm tiêu chí nổi bật hơn
Q48
  • Lưu PDF trong database riêng, gửi ID bản ghi: Claude không truy vấn được database của ứng dụng, chỉ thấy một chuỗi ID
  • Chuyển sang text, đặt sau phần case: mất bảng và ảnh trang; phần case thay đổi đứng trước nên không cache được policy
  • Tóm tắt policy mỗi quý: mất nguyên văn mà phân tích compliance phụ thuộc vào
Q49
  • Giữ client đồng bộ, tăng max_tokens: max_tokens chỉ quy định độ dài; phản hồi dài hơn làm mỗi lần chặn event loop lâu hơn
  • Tạo client đồng bộ mới cho mỗi request: lệnh gọi đồng bộ chặn event loop bất kể client nào; thêm overhead kết nối
  • Gọi client đồng bộ trong vòng polling 100 ms: lệnh đồng bộ chặn đến khi trả về, không có trạng thái chờ nào để poll
Q50
  • Viết lại cả module một lượt, review một PR: tạo đúng bản patch lớn mà reviewer từ chối; thay đổi bảo mật dễ bị bỏ sót
  • Chuyển sang permission mode tự duyệt edit: mất các điểm kiểm tra để bắt hướng sai sớm, vấn đề review dồn vào một diff lớn
  • Không chạy test hiện có, thêm test sau khi merge: mất bằng chứng hành vi được giữ nguyên; test sau merge không bảo vệ được thay đổi này
Q51
  • Tin mọi text khi user đã đăng nhập: xác thực chỉ định danh người dùng, không làm input an toàn; rủi ro injection nằm ở nội dung
  • Kích hoạt thanh toán khi giọng văn tự tin: giọng tự tin không chứng minh đúng, injection cũng tạo được text tự tin
  • Cho Claude quyền ghi trực tiếp mọi hồ sơ: trao quyền thay đổi không qua kiểm tra, trái least privilege
Q52
  • Đổi tên settings.json thành CLAUDE.md: CLAUDE.md là chỉ dẫn cho Claude, không phải cấu hình Claude Code; không chọn được model
  • Thêm cùng key model vào mọi file settings: precedence quyết định giá trị thắng, không phải số lần lặp; local vẫn đè project
  • Bỏ settings khỏi repo, thông báo qua chat: mỗi người tự cấu hình, không còn bản ghi chung nào, không kiểm tra hay ép được
Q53
  • Khôi phục mọi default, bỏ hết override: có thể mất hành vi workflow vẫn cần, ví dụ quy tắc phục hồi thêm sau sự cố thật
  • Giữ override ngắn nhất, bỏ override dài: độ dài code không cho biết override có cần hay không
  • Giữ tất cả vì lý do của tác giả gốc là đủ: yêu cầu và khả năng của SDK đã thay đổi, override có thể đã trùng tính năng SDK hỗ trợ sẵn
