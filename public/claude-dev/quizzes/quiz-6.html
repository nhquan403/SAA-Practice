1. Kiến trúc agent, Agent SDK & subagent

  • Workflow đi theo đường code định sẵn, hợp với việc đã rõ các bước; agent tự quyết quy trình, hợp với bài toán mở. Anthropic khuyên chọn giải pháp đơn giản nhất chạy được và kết hợp hai thứ khi cần: workflow cho phần kiểm tra thường lệ, chỉ gọi agent tại đúng điểm cần ra quyết định (ví dụ biểu mẫu có bố cục lạ). Đề nói "reliable routine processing, flexibility only at that point" là đáp án lai. Q8
  • Quy trình có nhiều giai đoạn, luật chuyển trạng thái rõ ràng, điểm duyệt của con người và có thể tạm dừng nhiều ngày thì mô hình hóa thành state graph (ví dụ LangGraph) với durable checkpoint để resume, interrupt cho bước duyệt, và chỉ gọi Claude bên trong các node cần phán đoán. Đừng để Claude "nhớ" trạng thái trong transcript hay tự chọn bước chuyển. Q4
  • Subagent chạy trong context riêng, chỉ trả kết quả cô đọng về hội thoại chính. Các việc điều tra độc lập, đọc nhiều file thì chạy song song bằng nhiều subagent rồi tổng hợp — vừa nhanh hơn vừa giữ context chính sạch. Q5
  • Muốn subagent chỉ đọc thì giới hạn trường tools của nó còn Read, Grep, Glob. Công cụ sửa file và shell khi đó không tồn tại trong session, nên read-only trở thành thuộc tính cấu hình chứ không phải lời nhờ trong prompt. Q6
  • Claude Agent SDK nhúng agent loop của Claude Code vào ứng dụng Python/TypeScript: có sẵn công cụ đọc/sửa file, chạy lệnh, permission, hooks và session. Job chạy tự động theo lịch thì dùng query với danh sách allowed tools + permission mode, lưu session ID để resume hôm sau. Client SDK thì phải tự viết loop; Messages API thuần không tự đọc file hay chạy lệnh. Q7
  • Dừng một lần chạy non-interactive bằng SIGTERM thì Claude Code thoát với exit code 143, bỏ dở turn và không ghi kết quả. Muốn kết thúc turn gọn gàng thì gửi SIGINT hoặc gọi interrupt() của Agent SDK trước khi dừng tiến trình. SIGKILL còn tệ hơn vì không dọn dẹp gì. Q16
  • Phân biệt sống còn: bước đã biết trước → workflow / state graph; quyết định phụ thuộc ngữ cảnh → agent. Đáp án "để agent tự do toàn bộ" hay "agent cân nhắc lại từng bước đã định" luôn thêm độ trễ và kém dự đoán. Q4, Q8

2. Context engineering, memory & compaction

  • Just-in-time context: thay vì nạp sẵn mọi tài liệu từ embedding search, agent giữ tham chiếu nhẹ (đường dẫn file, truy vấn đã lưu, link) rồi dùng tool để tải nội dung khi cần. Context tập trung vào bước hiện tại và agent thấy được cả file mới thêm trong lúc làm. Q1
  • Memory tool cho dự án nhiều session: một initializer session tạo progress log, checklist tính năng và con trỏ tới startup script; mỗi session sau đọc các file này trước. Chỉ đánh dấu tính năng xong sau khi kiểm thử end-to-end đạt, và cập nhật log trước khi session kết thúc. Ghi memory tùy hứng hay lưu nguyên transcript đều không giải quyết vấn đề. Q2
  • Compaction thay các message cũ bằng bản tóm tắt (log có compact_boundary), nên luật đặt trong prompt ban đầu có thể rơi mất. Luật lâu dài phải nằm trong CLAUDE.md nạp qua settingSources — nội dung này được re-inject mỗi request — kèm hướng dẫn cho compactor biết phải giữ gì. Q3
  • Context editing với chiến lược clear_tool_uses_20250919 xóa các tool result cũ nhất phía server khi context vượt ngưỡng, thay bằng placeholder. Vì xóa làm mất hiệu lực prompt cache, đặt clear_at_least để mỗi lần xóa giải phóng đủ token cho đáng lần ghi lại cache. Q9
  • Temperature chỉ điều khiển độ ngẫu nhiên khi sampling, không mở rộng context window. Transcript quá dài thì chia chunk hoặc tóm tắt các đoạn trước, dùng token counting để kiểm tra trước khi gửi. Trên Claude 4.7 trở lên, temperature khác mặc định còn trả lỗi 400. Q38
  • Format drift: JSON đúng ở đầu hội thoại nhưng sau vài lượt lại chèn văn xuôi, thiếu field, dù stop_reason vẫn là end_turn. Nguyên nhân nằm ở context — lịch sử dài làm loãng chỉ dẫn. Chẩn đoán bằng cách so request đầy đủ, rồi nhắc lại format gần cuối context, cắt lịch sử hoặc dùng structured outputs, và luôn validate trước khi dùng. Q44
  • Phân biệt sống còn: prompt caching giảm chi phí và độ trễ của phần prefix lặp lại, nhưng token đã cache vẫn tính vào context window. Đáp án nào hứa "cache để không chiếm context" là sai. Q1, Q9, Q38
  • Luật phải sống sót qua compaction → CLAUDE.md, không phải viết hoa, lặp lại trong prompt hay tắt compaction. Q3

3. Structured outputs & tool use

  • Structured outputs hỗ trợ JSON Schema có giới hạn: không hỗ trợ ràng buộc số như minimum và ràng buộc chuỗi như minLength/maxLength — dùng là lỗi 400 trước khi sinh. format: "email" thì được hỗ trợ. Bỏ các keyword không hỗ trợ khỏi schema rồi kiểm tra trong code sau khi parse. Đặt additionalProperties: true cũng không hỗ trợ; regex có lookahead hay {n,m} lớn cũng có thể lỗi 400. Q10
  • Thứ tự property: output giữ thứ tự trong schema, trừ việc các property required luôn đứng trước, rồi mới tới property tùy chọn. Code ghi CSV theo vị trí sẽ lệch cột — hãy map theo tên, hoặc đánh dấu mọi property là required. Q40
  • Python thay regex bóc tách văn xuôi bằng Pydantic model + messages.parse với structured outputs: nhận về object có kiểu, đúng tên field. Luật nghiệp vụ như khoảng giá trị confidence vẫn kiểm tra trên object sau khi parse. Q41
  • Structured outputs dùng constrained sampling với grammar đã biên dịch. Lần đầu dùng một schema sẽ tốn thêm độ trễ để compile; grammar được cache 24 giờ kể từ lần dùng cuối, nhưng mất hiệu lực khi cấu trúc schema đổi. Đổi tên hay description thì không ảnh hưởng. Dựng schema mới cho mỗi request là compile lại mỗi lần. Q42
  • Strict tool use chỉ bảo đảm tham số đúng schema (đúng kiểu, đủ field bắt buộc), không bảo đảm hành động được phép. Ứng dụng phải tự kiểm tra khách đang đăng nhập có sở hữu đơn hàng và đủ điều kiện hoàn tiền không, trả lỗi rõ ràng (is_error) nếu không — đây là rủi ro Broken Object Level Authorization. Q51
  • Phân biệt sống còn: schema đúng ≠ dữ liệu đúng nghiệp vụ ≠ hành động được phép. Schema lo hình dạng; giới hạn số/chuỗi và luật nghiệp vụ kiểm tra trong code; quyền truy cập kiểm tra trong code biết danh tính người dùng. Q10, Q41, Q51

4. Cấu hình Claude Code: settings, MCP & plugin

  • Phạm vi settings: .claude/settings.json được commit để cả team dùng chung; .claude/settings.local.json là ghi đè cá nhân theo dự án, Claude Code tự thêm vào git excludes khi tạo; ~/.claude/settings.json là settings người dùng cho mọi dự án trên một máy, không chia sẻ. Quyền (permission) nằm trong settings, không nằm trong CLAUDE.md hay prompt. Q27
  • Managed settings qua MDM (endpoint-managed) không tới được cloud session chạy trên môi trường của Anthropic. Cấu hình thêm server-managed settings trong admin console claude.ai cho cloud session, giữ file MDM trên laptop vì OS bảo vệ nó khỏi người dùng sửa. Cloud session chạy trên bản clone mới, không có settings.local.json hay settings người dùng. /status cho biết nguồn managed nào đang áp dụng. Q18
  • .mcp.json hỗ trợ mở rộng biến môi trường: ${VAR} chèn giá trị, ${VAR:-default} dùng mặc định nếu thiếu, áp dụng được cho url và headers của HTTP server. Nhờ vậy commit cấu hình chung mà không có token. Riêng credential của chính Claude Code như ANTHROPIC_API_KEY bị đọc thành rỗng trong url/headers của server từ xa. Q19
  • Tool search hoãn nạp định nghĩa tool MCP tới khi cần, chỉ tên tool và server instructions nạp lúc đầu. Nó bật mặc định nhưng tự tắt khi ANTHROPIC_BASE_URL trỏ tới host không phải first-party (vì đa số proxy không chuyển tiếp block tool_reference). Gateway có chuyển tiếp thì đặt ENABLE_TOOL_SEARCH=true. Q11
  • Auto-update plugin bật mặc định cho marketplace chính thức và marketplace thêm từ claude.ai, tắt mặc định cho marketplace khác (kể cả của bên thứ ba). Bật trong tab Marketplaces của /plugin, hoặc chạy claude plugin update <plugin>@<marketplace> để cập nhật ngay. /reload-plugins chỉ nạp lại bản đã có trên đĩa. Q12
  • Phân biệt sống còn: endpoint-managed (MDM) chỉ phủ máy của dev; server-managed phủ cả cloud session. Tổ chức có cloud session thì cần cả hai. Q18

5. Mở rộng Claude Code: hooks, skills & output style

  • Hook PreToolUse chạy trước khi tool thực thi và chạy trước cả việc kiểm tra permission mode, nên quyết định deny chặn được lệnh ngay cả ở bypassPermissions. Trả về deny kèm lý do nêu rõ pattern bị chặn để Claude biết và chọn hướng an toàn hơn (ví dụ chạy trên staging). PostToolUse chạy sau khi lệnh đã chạy xong — quá muộn để ngăn chặn. Q46
  • Prompt-based hook (type: "prompt") gửi hook input và prompt của team tới một model Claude, model trả JSON có quyết định. Sự kiện Stop hỗ trợ loại hook này — hợp với câu hỏi "công việc đã xong chưa" vốn cần đọc hiểu hội thoại. SessionStart chỉ hỗ trợ command và MCP tool hook. Cần truy cập tool thì có agent hook. Q50
  • Output style (Explanatory, Learning, Concise…) định hình mọi phản hồi trong session, mỗi người tự chọn cho session của mình. CLAUDE.md chứa kiến thức dự án (lệnh build, quy ước) và vẫn nạp bất kể style nào. CLAUDE.md lo Claude cần biết gì, output style lo Claude trả lời thế nào. Q49
  • Skill là bộ chỉ dẫn tái sử dụng, nạp theo nhu cầu: đầu session chỉ thấy description ngắn, nội dung đầy đủ nạp khi task khớp. Quy trình thuần chỉ dẫn, dùng thỉnh thoảng → project skill trong .claude/skills. CLAUDE.md nạp toàn bộ mỗi session nên nên giữ ngắn. Q52
  • Skill vs MCP server: Skill đóng gói chỉ dẫn, script và tài nguyên, nạp lũy tiến (metadata → chỉ dẫn → tài nguyên). MCP server phơi bày tools, resources, prompts qua giao thức chuẩn để kết nối hệ thống sống như đơn hàng, tồn kho. Hai thứ bổ trợ nhau: Skill có thể hướng dẫn cách dùng tool MCP. Ranh giới không phải đọc hay ghi dữ liệu. Q53
  • Phân biệt sống còn: CLAUDE.md / prompt là hướng dẫn, hook là cưỡng chế. Cần "chặn dù người dùng đổi mode hay lỡ duyệt" thì phải là PreToolUse hook trả deny. Q46
  • Chọn đúng cơ chế: luôn áp dụng cho mọi phản hồi → output style; kiến thức dự án → CLAUDE.md; quy trình dùng thỉnh thoảng → skill; hệ thống bên ngoài, dữ liệu sống → MCP; cô lập context → subagent. Q49, Q52, Q53

6. Model, tham số API & chi phí

  • Effort là tham số request trong output_config. Hầu hết model mặc định high, riêng Claude Opus 5.5 và Claude Haiku 5.5 mặc định medium. Effort thấp → ít tool call, phản hồi ngắn hơn. Chuyển từ Sonnet 5.5 sang Opus 5.5 mà thấy phân tích ngắn đi thì đặt effort high rồi chạy lại eval. Q31
  • Adaptive thinking: trên Claude 4.7 trở lên (kể cả Sonnet 5.5), gửi thinking với type: "enabled" trả lỗi 400 bất kể budget_tokens. Chuyển sang type: "adaptive", bỏ budget_tokens, điều khiển độ sâu bằng effort; header beta interleaved-thinking có thể bỏ. Lưu ý hành vi sẽ khác: Claude tự quyết có nghĩ hay không, ở effort thấp có thể không nghĩ với câu dễ. Q32
  • Fast mode chạy cùng model với cấu hình suy luận nhanh hơn, output nhanh tới 2.5 lần (lợi về output tokens per second, không phải time to first token), giá cao hơn mức chuẩn. Đổi giữa fast và standard làm mất prompt cache. Không dùng được với Batch API. Q30
  • Long context pricing: Claude 4.6 trở lên tính giá chuẩn cho toàn bộ context window, trừ Haiku 5.5 — prompt trên 100,000 token chịu giá cao hơn, và độ dài prompt tính mọi input token kể cả cache read/write. Giá tính theo từng request, không lan sang cả hội thoại. Q36
  • Chọn model khi chất lượng, độ trễ, chi phí đều ràng buộc: đánh giá cả ba cùng lúc trên workload thật (bộ eval từ ticket thật), không chốt theo benchmark công khai hay xét chi phí sau. Q37
  • Rate limit đo bằng request và token mỗi phút. Client HTTP thô đọc header anthropic-ratelimit-* (remaining, reset) để tự giãn nhịp, và tôn trọng retry-after khi vẫn dính 429. Q23
  • Kiểm chứng cost model: kéo dữ liệu từ Usage and Cost API, nhóm theo workspace và model, tách uncached input, cache read/write, output, server tool rồi so với dự báo — trước khi đổi bất kỳ setting nào. Q35
  • Phiên bản SDK Python nhìn chung theo SemVer nhưng một số thay đổi không tương thích (kể cả chỉ đổi kiểu tĩnh) có thể ra ở bản minor. Pin chính xác trong lockfile, nâng cấp theo lịch qua pull request có chạy type check và test. Q34
  • Phân biệt sống còn: max_tokens chỉ giới hạn độ dài một phản hồi. Nó không tăng độ sâu suy luận, không giảm số request, không cứu format drift (khi đã end_turn), không mở rộng context. Chỉ có ý nghĩa khi stop_reason là max_tokens. Q23, Q31, Q44

7. Files API & Message Batches

  • File upload thuộc về workspace, không gắn với người dùng cuối, hội thoại hay key đã upload. Mọi key có quyền vào workspace đều đọc được. Vì vậy đừng bao giờ nhận file_id từ client: giữ ID phía server, map tài liệu theo khách trong database và kiểm tra quyền sở hữu; ứng dụng multi-tenant nên tách mỗi khách một workspace. Q13
  • File tồn tại tới khi bị xóa bằng DELETE /v1/files/{file_id} hoặc tới expires_at. File không đặt hết hạn thì tồn tại mãi; file đã hết hạn vẫn giữ metadata tới 30 ngày. Không đổi tên được file sau khi upload. Ngừng một ứng dụng phải chủ động xóa file và thu hồi API key của workspace. Q20
  • Chỉ file do skills hoặc code execution tool tạo ra mới tải xuống được ("downloadable": true). Tải file mình đã upload trả lỗi 400 — muốn có bản lưu kiểm toán thì giữ bản gốc trong storage của ứng dụng. Q22
  • Kết quả batch có 4 loại: succeeded, errored, canceled, expired. Chỉ gửi lại request expired và errored do lỗi server; request không hợp lệ phải sửa trước. Thứ tự kết quả không được bảo đảm → gán custom_id duy nhất và join theo ID. Q24
  • Kết quả Message Batch chỉ tải được trong 29 ngày kể từ khi tạo batch; sau đó batch vẫn hiện trong danh sách nhưng kết quả mất. Giới hạn 24 giờ là thời gian xử lý, không phải thời gian lưu. Tải và lưu kết quả về storage riêng ngay khi batch kết thúc. Q33
  • Phân biệt sống còn: expiration là tính năng vòng đời, không phải kiểm soát truy cập hay bảo đảm xóa. Cách ly dữ liệu = workspace + kiểm tra sở hữu phía server; dọn dữ liệu = xóa chủ động + thu hồi key. Q13, Q20

8. Yêu cầu, đánh giá & quản lý thay đổi

  • Yêu cầu chức năng mô tả hệ thống làm gì (trả lời số dư, chuyển máy cho nhân viên khi khách yêu cầu). Yêu cầu hạ tầng/hiệu năng mô tả tải và tốc độ phải đáp ứng (300 cuộc gọi đồng thời, âm thanh đầu tiên trong 800 ms) — quyết định rate-limit tier, capacity, load test, streaming. Q14
  • Tiêu chí thành công tốt phải cụ thể, đo được, khả thi, liên quan. Biến từ mơ hồ ("chính xác, ngắn gọn, nhanh") thành ngưỡng số trên tập held-out: độ phủ nghĩa vụ so với bản tham chiếu, giới hạn số từ, độ trễ ở percentile 95. Q15
  • Thay đổi một handler dùng chung (thêm loại content block mới) cần unit test cho từng loại block, kể cả loại chưa biết, cộng integration test luồng phản hồi đầy đủ — vì tài liệu streaming khuyên xử lý êm các event chưa biết. Q21
  • Tham số bị deprecate có thay thế hành xử khác ở edge case: viết regression check trước, rồi migrate từng nhóm call site và validate mỗi nhóm. Biên dịch được không chứng minh kết quả không đổi. Q25
  • Đổi prompt có thể đổi ý nghĩa output mà tên field vẫn giữ nguyên. Trước rollout chung, đánh giá từng hợp đồng downstream (cấu trúc, nghĩa field, giá trị cho phép) và phối hợp với chủ hệ thống. Regression eval nên đạt gần 100% trước khi ship. Q26
  • Nhiều đề xuất sửa prompt mà không ai chứng minh được: gom các ca lỗi đại diện, ghi đáp án đúng, thêm vào bộ eval rồi so từng phương án trên cùng bộ đó. Ví dụ nên liên quan và đa dạng. Q39
  • Phân biệt sống còn: bằng chứng phải có trước khi duyệt/ship — test lặp lại được, eval trên tập đại diện. Ảnh chụp màn hình, demo 5 mẫu tự chọn, hứa viết test sau, model tự chấm điểm đều không phải bằng chứng. Q15, Q21, Q39

9. Vận hành, truy vết & bảo mật

  • Mỗi response có header request-id (trong body lỗi là request_id), SDK Python/TypeScript lộ ra qua thuộc tính _request_id. Đây là thứ Anthropic support cần để tìm đúng request. Log kèm model ID và phiên bản prompt template để nhóm theo cấu hình; không log API key hay nguyên hội thoại dạng plain text. Q17
  • Stream trả HTTP 200 rồi mới có error event giữa chừng, nên phải lấy request ID từ chính response và ghi cùng loại error event (ví dụ overload) để báo support. Q28
  • Điều tra refusal: mở trace đầy đủ — system prompt, message trước, văn bản retrieve, chi tiết response (stop_reason: "refusal", streaming refusal có stop_details với category và giải thích) — rồi so với trace thành công. Chỉ nhìn câu hỏi người dùng hay thống kê tổng hợp không tìm ra nguyên nhân. Q29
  • Giảm hallucination: kiểm chứng claim quan trọng với nguồn tin cậy trước khi hệ thống downstream coi là sự thật; giới hạn Claude vào tài liệu cung cấp, yêu cầu trích dẫn, dùng citations. Lời văn tự tin, điểm confidence model tự gán, hay nhiều lần sinh trùng nhau đều không chứng minh đúng. Q43
  • API key bị lộ công khai và có usage lạ: revoke ngay trong Console, tạo key mới, lưu vào secrets manager. Xóa lịch sử git, chuyển sang .env hay chờ support xác nhận đều để key cũ tiếp tục bị dùng. Q45
  • Threat model cho ứng dụng LLM bổ sung: prompt injection (trực tiếp và gián tiếp qua nội dung retrieve như tài liệu đối tác), jailbreak, rò rỉ dữ liệu trong context, output không an toàn vượt qua kiểm soát. OWASP xếp prompt injection đứng đầu rủi ro ứng dụng LLM. Q47
  • Least privilege trong Console: Workspace Developer tạo/quản lý API key và dùng API; chỉ Workspace Admin chỉnh settings và thành viên. Organization admin tự động có quyền Workspace Admin ở mọi workspace. Thêm contractor chỉ vào sandbox với vai trò developer. Q48
  • Phân biệt sống còn: request ID mới là định danh — timestamp, model, hash nội dung hay prompt đầy đủ đều không giúp support tìm đúng request. Q17, Q28
  • Ranh giới bảo mật phải nằm ở cấu hình và code (role, workspace, kiểm tra sở hữu, revoke key), không nằm ở lời dặn trong văn bản hay prompt. Q45, Q48, Q51

13. Mẹo làm bài thi

  • Tìm chữ "enforce", "even if", "must never". Những từ này loại ngay mọi đáp án chỉ dựa vào lời dặn trong prompt, CLAUDE.md hay tool description. Đáp án đúng là cấu hình hoặc code: danh sách tool, hook, role, kiểm tra trong ứng dụng. Q6, Q46, Q51
  • Đề yêu cầu "diagnose first" hay "before anyone changes settings" thì chọn đáp án thu thập bằng chứng. Loại các đáp án đổi model, hạ max_tokens, đổi prompt khi chưa xem trace hay dữ liệu usage. Q29, Q35, Q44
  • Đáp án "tăng max_tokens" gần như luôn là mồi nhử. Chỉ đúng khi stop_reason là max_tokens. Đề cho sẵn end_turn là để bạn loại nó. Q31, Q44
  • Câu "Select two" thường là hai nửa bổ trợ nhau. Ví dụ giữ file_id phía server và tách workspace Q13, xóa file và revoke key Q20, PreToolUse hook và deny kèm lý do Q46, output style và CLAUDE.md Q49.
  • Model tự đánh giá không bao giờ là bằng chứng. Tự chấm điểm, tự gán confidence, tự khẳng định đúng schema, sinh nhiều lần cho trùng nhau — đều bị loại. Q15, Q43, Q44
  • Đề nhắc tên model cụ thể (Opus 5.5, Haiku 5.5, Sonnet 5.5) là có chi tiết riêng của model đó. Effort mặc định, long context pricing, adaptive thinking. Q31, Q32, Q36
  • Ưu tiên giải pháp có sẵn, ít code nhất. Đề nói "minimal custom code" hay "prefers configuration" thì chọn tính năng tích hợp sẵn (context editing, prompt hook, Agent SDK) thay vì tự viết. Q7, Q9, Q50
  • Bằng chứng trước, kết luận sau. Đáp án viết tóm tắt trước rồi mới review, hay release trước rồi xem thực tế, đều đảo ngược thứ tự. Q5, Q39

14. Bẫy thường gặp

  • Token đã cache vẫn chiếm context window. Caching chỉ giảm chi phí và độ trễ. Q1, Q9, Q38
  • Strict tool use / structured outputs không phải phân quyền. Đúng schema không có nghĩa là được phép. Q51
  • File thuộc workspace, không thuộc key hay người dùng. Xoay key hay đặt hết hạn không chặn được việc khách dùng file_id của người khác. Q13, Q20
  • Managed settings qua MDM không tới cloud session. Q18
  • Thứ tự kết quả batch không được bảo đảm. Luôn join bằng custom_id. Q24
  • Giới hạn 24 giờ của batch là thời gian xử lý, còn kết quả lưu 29 ngày — không kéo dài được. Q33
  • Không tải xuống được file mình đã upload. Chỉ file do skills/code execution tạo ra. Q22
  • Required property luôn đứng trước trong output. Đổi thứ tự trong schema không cứu được code đọc theo vị trí. Q40
  • Đổi tên/description schema không làm mất grammar cache, đổi cấu trúc mới làm mất. Q42
  • Fast mode không phải model nhỏ hơn và không rẻ hơn. Cùng model, giá cao hơn, đổi tốc độ làm mất cache. Q30
  • Opus 5.5 "kém" hơn Sonnet 5.5 có thể chỉ vì effort mặc định là medium. So sánh phải cùng effort. Q31
  • Không có setting nào khiến adaptive thinking giống hệt budget cố định cũ, kể cả effort max. Q32
  • /reload-plugins không tải bản mới từ marketplace. Q12
  • Gói MCP server vào plugin không làm nó nạp lười. Plugin đổi cách phân phối, không đổi cách nạp tool. Q11
  • Gửi SIGKILL hay coi exit 143 là thành công đều sai. Dùng SIGINT/interrupt(). Q16
  • Tên field giữ nguyên không có nghĩa là ý nghĩa giữ nguyên. Q26
  • Organization admin tự động là Workspace Admin ở mọi workspace — không dùng cho contractor. Q48
