1. Chọn kiến trúc: đơn giản trước & các mẫu workflow

  • Đơn giản ≠ thiếu: prototype một lần gọi + retrieval đã đạt mục tiêu thì ship, giữ eval làm baseline → dấu hiệu đề "sau này có thể khó hơn" Q4
  • Quy trình cố định: Messages API + output schema, kiểm quy tắc bằng code → dấu hiệu đề "trích xuất hóa đơn rồi đối chiếu" Q6
  • Framework che prompt: xem prompt, tool, history thật qua tracing, gỡ lớp trừu tượng → dấu hiệu đề "không ai biết Claude nhận gì" Q2
  • Prompt chaining: các bước tuần tự, gate code ở giữa, truyền category đã kiểm sang bước sau → dấu hiệu đề "muốn xem phân loại trước" Q10
  • Parallelization ≠ orchestrator-workers: subtask biết trước → subagent song song + coordinator tổng hợp một khuyến nghị; không đoán trước → orchestrator Q5

2. Agent SDK, subagent & trạng thái bền vững

  • LangGraph interrupt: PostgresSaver + thread_id ổn định, resume bằng Command; side effect đặt sau interrupt hoặc idempotent → dấu hiệu đề "email gửi trùng" Q1
  • Tự host Agent SDK: mỗi session một container, SessionStore mirror transcript để resume trên pod khác → dấu hiệu đề "vận hành sở hữu runtime" Q7
  • Messages API stateless: không tự chạy tool, không giữ trạng thái giữa request Q7
  • AgentDefinition: model ghi đè model subagent, description quyết định có được giao việc → dấu hiệu đề "description helper, subagent đắt" Q8
  • Explore subagent: read-only, đọc nhiều file trong context riêng, chỉ trả tóm tắt; thứ tự explore → plan → code Q41

3. Tool use, structured output & kiểm chứng kết quả

  • Poka-yoke tool: đổi tham số để khó sai, ví dụ bắt đường dẫn tuyệt đối → dấu hiệu đề "đổi thư mục, sai đường dẫn" Q3
  • Anthropic-schema tool: text_editor/bash được huấn luyện sẵn, app vẫn tự thực thi → dấu hiệu đề "tool tự định nghĩa, tham số sai" Q51
  • Tool lỗi: tool_result với is_error: true + loại lỗi, không trả "thành công" giả → dấu hiệu đề "không lưu được nhưng báo OK" Q53
  • Trường có thể vắng: anyOf string/null, vẫn required, dặn trả null; minLength không hỗ trợ → dấu hiệu đề "giá trị bịa" Q12
  • Hình dạng ≠ giá trị: kiểm stop_reason = end_turn, đối chiếu nguồn thật, duyệt người khi rủi ro cao Q40, Q12
  • Tự chấm tự tin / lặp giống nhau: chỉ chứng minh nhất quán, không chứng minh đúng Q40
  • Parser: table-driven test với text, tool_use, refusal, max_tokens; refusal là response thành công bình thường Q23

5. Cấu hình & quy trình làm việc với Claude Code

  • Import @path ≠ link thường: @path nạp lúc khởi động, lồng tối đa 4 tầng; link và README không nạp → dấu hiệu đề "bản copy lệch nhau" Q24, Q26
  • Scope CLAUDE.md: chuẩn chung ở managed/user scope, build command ở repo; CLAUDE.local.md chỉ cho sở thích cá nhân Q26, Q24

  • Debug hook: --debug ghi vào ~/.claude/debug/<session-id>.txt; đọc log trước, matcher có thể thiếu Edit → dấu hiệu đề "không in gì" Q28
  • Ghim model trên Bedrock/Vertex: ANTHROPIC_DEFAULT_OPUS_MODEL trong managed settings → dấu hiệu đề "alias fallback model cũ" Q21
  • Tự kiểm ≠ review độc lập: test/build có sẵn để lặp đến pass, rồi subagent review context mới, rồi người review Q19

6. Prompt engineering, context engineering & retrieval

  • Khóa định dạng: 3–5 ví dụ đa dạng trong <example>, chạy lại eval; chữ in hoa không đủ → dấu hiệu đề "giá trị trôi định dạng" Q39
  • XML tag: tách <examples>, <input>, <instructions>, output trong <reply> → dấu hiệu đề "chép chi tiết từ ví dụ" Q44
  • Context engineering: chọn, duy trì tập token nhỏ nhất nhiều tín hiệu nhất suốt quá trình chạy; mở rộng prompt engineering Q38
  • Contextual Retrieval: Claude viết context riêng từng chunk, chèn trước embedding và BM25 → dấu hiệu đề "chunk không rõ sản phẩm" Q43
  • Prompt caching: phần chung lên trước, breakpoint sau đó, dữ liệu khách sau; kiểm cache_read_input_tokens Q14
  • Tọa độ ảnh: theo ảnh đã resize (1920×1080 → 1456×819); resize trước hoặc quy đổi → dấu hiệu đề "lệch đều" Q25

7. Model, thinking, token & chi phí

  • Chọn model: làm rõ tiêu chí chất lượng, latency, chi phí trước, rồi so trên eval dữ liệu thật Q30
  • Efficiency-first: việc đơn giản, khối lượng lớn → bắt đầu Haiku, nâng cấp khi eval cho thấy thiếu → dấu hiệu đề "hàng triệu tin" Q37
  • Adaptive thinking: câu dễ không có thinking block là thiết kế; muốn nghĩ nhiều thì tăng effort Q32
  • Summarized thinking: tính tiền toàn bộ thinking token, không theo bản tóm tắt; đối soát bằng usage Q34
  • Tokenizer mới (4.7+): ~30% token nhiều hơn; đếm lại bằng token counting endpoint, sửa max_tokens, ngân sách Q33
  • Server-side fallback: usage từng attempt ở usage.iterations, top-level không cộng dồn; xem trường model Q35
  • Rate limit tách chiều: RPM, ITPM (input chưa cache), OTPM; vượt chiều nào cũng 429, xin nâng trước launch Q18
  • Hóa đơn tăng nhanh hơn traffic: ghi usage theo tính năng, mỗi tính năng một key, xem Usage and Cost API Q31

8. Yêu cầu, đánh giá & vận hành

  • "Phải nhanh": TTFT < 2s bằng streaming + thời gian hoàn tất theo p95, đo trong production Q16
  • Functional ≠ infrastructure: gán nhãn ticket là functional (accuracy); chạy khi region sập là availability (failover) Q22
  • Failover Bedrock: thiếu Files API, web search, Batches; model ID riêng → liệt kê, thiết kế đường dự phòng, test Q17
  • Việc chạy hàng phút: 202 Accepted + job ID, worker streaming, client poll → dấu hiệu đề "proxy cắt kết nối" Q20
  • Sau release: monitoring, sự cố, chủ sở hữu vận hành; test model mới trước ngày retire Q9
  • Migration model: chỉnh prompt cho model mới, chạy eval + regression (~100%), chỉ chuyển khi hết regression Q29
  • Output dao động: nhiều trial mỗi case, so tỉ lệ; Messages API không có seed Q36
  • Quá ít test case: Claude sinh edge case từ seed, review expected, chấm bằng code Q42

9. Bảo mật, guardrails & cô lập dữ liệu

  • Cô lập khách: truy xuất theo client ID từ session đã xác thực; cache chỉ tách theo workspace Q14
  • Defense in depth: nhiều lớp input, quyền tool, output; nội dung truy xuất không tin cậy; middleware lỗi → fail closed Q45
  • Dữ liệu cấm gửi ra: redact trước khi rời ứng dụng; mã hóa đường truyền không thay được → dấu hiệu đề "mã cửa, badge" Q46
  • Mỗi hệ thống một API key: workspace có spend/rate limit riêng, thu hồi đúng một key → dấu hiệu đề "không biết ai gây spike" Q47
  • Harmlessness screen: Haiku + structured output ra verdict, coi refusal là harmful → dấu hiệu đề "jailbreak, rẻ, nhanh" Q48
  • Lời dặn ≠ thực thi: prompt an toàn cần có nhưng không là lớp duy nhất Q45, Q48

Học đáp án đúng chỉ giải được đúng câu đó. Hiểu vì sao từng đáp án sai lại sai giúp nhận diện được cả họ câu hỏi tương tự, kể cả khi đề đổi cách hỏi. Mỗi dòng dưới đây là một câu, liệt kê các đáp án sai và lý do sai thật sự — đúc kết từ chính phần giải thích của đề, không phải suy đoán.

  • Coi token count như nhau giữa các model, đi soi tài liệu: tokenizer mới sinh nhiều token hơn; input không đổi, cách tách token mới đổi
  • Bật prompt caching để token không tính vào context: cached token vẫn chiếm context window; caching chỉ đổi giá và tốc độ
Q34
  • API tính output theo mức max_tokens: max_tokens chỉ là giới hạn; tính tiền theo token thực sinh, kể cả thinking
  • Display đang ẩn nhầm, chuyển sang hiện chuỗi suy nghĩ thô: không có tùy chọn hiện bản thô; bản tóm tắt là có chủ đích
  • Cached input bị tính vào output: cached token báo ở phần input usage, không làm phình output
Q35
  • Đọc tiếp usage cấp cao nhất vì API đã cộng dồn: tài liệu nói ngược lại — usage cấp cao chỉ là attempt trả về, token các model không bao giờ cộng gộp
  • Tính mọi request theo giá model yêu cầu, attempt bị từ chối miễn phí: attempt có output đều bị tính, kể cả bị từ chối giữa chừng; fallback tính theo giá model fallback
  • Tắt fallback, retry tay vì response không cho biết model nào trả lời: trường model và fallback content block có cho biết; tắt chỉ thêm round trip
Q36
  • Mỗi bản chạy một lần, chọn điểm cao hơn: chênh vài case có thể chỉ là nhiễu; dao động giữa các lần chạy có thể đảo thứ hạng
  • Cố định random seed: Messages API không có seed cho output xác định; dù cố định được cũng che mất dao động người dùng thực gặp
  • Kỹ sư xem response đầu tiên mỗi case: lặp lại vấn đề một mẫu; kỳ vọng của một người không phải tiêu chí thành công được định nghĩa
Q37
  • Chọn model đứng đầu leaderboard: benchmark công khai đo tác vụ chung, không phải nhãn, tin nhắn hay giới hạn latency của team
  • Bắt đầu với model mạnh nhất rồi hạ max_tokens: độ dài output chỉ là một phần latency; model lớn chậm và đắt hơn mỗi token, output phân loại vốn đã ngắn
  • Chọn model có context window lớn nhất: tin nhắn ngắn chiếm rất ít window; kích thước context là giới hạn dung lượng, không phải chất lượng
Q38
  • Prompt engineering cho chỉ dẫn, context engineering chỉ cho database ngoài: context engineering quyết định cái gì vào input của Claude mỗi bước, và hai việc chồng lấn nhau
  • Context engineering chỉ quản lý input người dùng, loại tool result: tool result, system instruction, trạng thái tích lũy mới là phần lớn context của một review dài
  • Context engineering là tăng kích thước window: window là thuộc tính của model; window lớn không tự quyết thông tin nào liên quan
Q39
  • Viết hoa tên trường ở đầu và cuối, thêm cảnh báo: Claude đã sinh đủ sáu trường; chữ in hoa không cho biết thang severity hay độ dài, còn có thể gây sửa quá tay
  • Thêm toàn bộ runbook làm bối cảnh: cải thiện nội dung chứ không nói cách biểu đạt severity; tăng kích thước prompt và latency
  • Hạ temperature xuống tối thiểu: không làm output hoàn toàn xác định, model hiện tại từ chối temperature tùy chỉnh; không có ví dụ thì chẳng có gì để nhất quán theo
Q40
  • Áp dụng ngay vì đã đúng schema: đúng schema chỉ là đúng kiểu và cấu trúc, không cho biết service có tồn tại hay limit có hợp lý
  • Cho Claude tự chấm độ tự tin, từ 8 trở lên thì áp dụng: điểm tự chấm là một output nữa, không phải kiểm tra độc lập; Claude có thể sai mà vẫn tự tin
  • Hỏi lại ba lần, giống nhau thì áp dụng: đồng thuận chứng minh nhất quán chứ không phải đúng; prompt hoặc dữ liệu sai thì cả ba cùng sai, tốn gấp ba
Q41
  • Dán mọi file nhắc đến currency vào hội thoại chính: lấp context chính bằng tài liệu phần lớn không liên quan; độ chính xác và recall giảm khi context lớn
  • Tìm trong hội thoại chính, dặn bỏ qua file không liên quan: file đã đọc vẫn nằm trong context dù được dặn bỏ qua; cô lập cần context riêng
  • Viết thay đổi trước, tìm kiếm sau: sửa trước khi hiểu dễ làm hỏng nơi gọi; khám phá phải đi trước triển khai
Q42
  • Thay chỉ dẫn bằng danh sách dài ví dụ sinh tự động: mất các quy tắc định nghĩa cách xử lý mâu thuẫn; vẫn không có bộ eval để đo
  • Thêm MUST, CRITICAL đến khi qua 12 case vừa lỗi: nhấn mạnh theo lỗi gần nhất dễ overfit và sửa quá tay ở chỗ khác; cần đo lường chứ không cần chữ mạnh hơn
  • Đổi model sau mỗi case lỗi: một response không cho biết model nào tốt hơn vì output dao động; chỉ chạy theo nhiễu
Q43
  • Gắn cùng một bản tóm tắt cả manual cho mọi chunk: Anthropic ghi nhận tóm tắt chung chỉ cải thiện rất ít; không nói được từng chunk nói về gì
  • Tăng chunk lên gấp năm: loãng độ liên quan, thêm text thừa vào prompt, precision có thể giảm; chunk vẫn thiếu thông tin nhận diện
  • Bỏ retrieval, nhét mọi manual vào prompt: hàng nghìn manual vượt xa sức chứa và rất chậm, đắt; chỉ hợp với knowledge base nhỏ
Q44
  • Thêm câu "không được chép từ ví dụ", giữ prompt trộn lẫn: nên nói Claude cần làm gì thay vì không làm gì; ví dụ và ticket thật vẫn lẫn vào nhau
  • Bỏ hết ví dụ: ví dụ là cách đáng tin để định giọng văn và cấu trúc; vấn đề là ví dụ chưa được đánh dấu
  • Tăng temperature: ngẫu nhiên hơn không cho Claude biết đâu là ví dụ, đâu là ticket; có thể bị từ chối trên model hiện tại và không giúp gì cho parser
Q45
  • Chỉ kiểm bản nháp cuối, bỏ ngỏ retrieval và tool: quá muộn để hoàn tác retrieval hay tool call trái phép; dồn bảo vệ vào một chỗ
  • Gom kiểm soát vào middleware, cho request qua khi timeout: tạo đường không được bảo vệ đúng lúc thành phần lỗi; phải fail closed
  • Một system prompt an toàn toàn diện làm lớp duy nhất: prompt hướng dẫn chứ không thực thi; không tạo ranh giới độc lập cho retrieval, tool, xuất bản
Q46
  • Lọc mẫu badge phổ biến trước, thêm mã cửa sau khi monitoring phát hiện: chính sách áp cả hai từ đầu; cố ý để hở là gửi giá trị bị cấm, monitoring chỉ thấy sau khi vi phạm
  • Gửi nguyên note qua kết nối mã hóa: mã hóa chống nghe lén trên đường truyền, không ngăn service đích nhận giá trị bị cấm
  • Dặn Claude bỏ qua badge và mã cửa: request đã vượt ranh giới khi Claude đọc được; lời dặn không hoàn tác được việc gửi
Q47
  • Giữ một key, rotate hằng tuần: hạn chế thời gian key lộ còn dùng được, nhưng vẫn không quy được usage, thu hồi vẫn dừng cả ba hệ thống
  • Giữ một key, thêm metadata tên hệ thống: metadata do bên gọi tự khai, có thể thiếu hoặc sai; không cô lập limit hay credential
  • Giữ một key trong secrets manager cấp cho cả ba: bảo vệ bản thân key, nhưng vấn đề quy trách nhiệm và phạm vi ảnh hưởng y nguyên
Q48
  • Thêm một câu vào system prompt, để model chính tự phán: input cố ý soạn ra để vượt đúng loại hướng dẫn này; không phải lớp kiểm tra riêng trước hội thoại
  • Chạy model chính hai lần, trả lời rồi tự chấm: gấp đôi chi phí và latency; câu trả lời đã sinh trước khi được sàng lọc
  • Ghi log, review hằng tuần, gỡ bài sau: phát hiện sau khi bài độc hại đã công khai trên forum

  • Chọn theo tiền lệ tool tự viết trước đây: tiền lệ giúp ước tính nhưng không cho biết năng lực này nên mở rộng hay viết mới
  • Viết tool riêng ngay để toàn quyền kiểm soát: bỏ qua so sánh; phần mở rộng được hỗ trợ có thể đáp ứng với ít code bảo trì hơn
