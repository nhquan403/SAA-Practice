1. Yêu cầu nghiệp vụ, chọn model & chi phí

  • Yêu cầu đi trước công nghệ. Khi đã có mục tiêu nghiệp vụ mà engineering chưa có gì để làm, việc đầu tiên là dịch mục tiêu đó thành yêu cầu chức năng và yêu cầu hạ tầng rõ ràng: input, output, tích hợp, tiêu chí chấp nhận, ràng buộc latency và xử lý dữ liệu. Anthropic khuyên bắt đầu bằng tiêu chí thành công cụ thể, đo được, rồi chọn giải pháp đơn giản nhất đáp ứng chúng. Model tier, framework hay "mẫu của công ty khác" chỉ được cân nhắc sau khi có yêu cầu — đề nào cho đáp án "chọn framework/model trước" là bẫy. Q1
  • Hai loại việc có nhu cầu rất khác nhau (400.000 ticket phân loại thường mỗi ngày và vài trăm appeal cần suy luận nhiều bước) phải được đánh giá riêng trên bộ dữ liệu đại diện của từng loại, rồi định tuyến mỗi loại sang tier rẻ nhất đạt ngưỡng của nó. Điểm trung bình gộp bị số lượng lớn chi phối nên che mất phần appeal; benchmark công khai chỉ để shortlist. Trước khi đổi sang thế hệ model mới phải chạy lại cả hai bộ eval. Q29
  • Giá input và output khác nhau, và output đắt hơn input. Ví dụ trong giải thích: Claude Sonnet 5.5 có giá $2 mỗi triệu input token và $10 mỗi triệu output token. Dự báo phải tính riêng input và output theo usage thực tế, cộng các mức giảm giá áp dụng: cache read chỉ bằng một phần nhỏ giá input, Batch API bằng 50%. Billing tính theo token thực sinh, không theo max_tokens. Q38
  • Job chạy đêm, kết quả cần trước sáng hôm sau, cùng một policy 30.000 token cho 8.000 tài liệu: hai đòn giảm chi phí lớn nhất là đưa policy lên đầu request với cache breakpoint (để mọi request có chung prefix) và Message Batches API (giá 50%). Hai cách này cộng dồn được và không đụng tới chất lượng. Q48
  • Pin model ID cụ thể cho môi trường cần kiểm toán. Một model ID trỏ tới một snapshot cố định — Anthropic không cập nhật weights của ID đã có, phiên bản mới ra dưới ID mới. ID không ngày của thế hệ 4.6 cũng là snapshot cố định, không phải pointer tự cập nhật. Ngược lại, alias của model cũ trỏ tới snapshot mới nhất nên có thể đổi ngầm. Ghi lại model ID trả về trong mỗi response cạnh kết quả, và chỉ đổi ID sau eval và phê duyệt. Q52

2. Prompt engineering & tài liệu đầu vào

  • Hãy coi Claude như một nhân viên mới rất giỏi nhưng chưa biết ngữ cảnh của team. Mã nhãn như L-ESC-2 không mang nghĩa gì; cách sửa là định nghĩa từng nhãn, nói rõ cách phân biệt với nhãn gần giống, và giải thích nhãn được dùng thế nào ở downstream để Claude khái quát được cách diễn đạt lạ. Viết hoa, nhấn mạnh hay tăng temperature đều không bổ sung thông tin còn thiếu. Q2
  • Multishot prompting: khi cần cố định cấu trúc đầu ra (heading, thứ tự section, độ chi tiết) và đã có cặp input–output được duyệt, đưa chúng vào prompt làm ví dụ. Anthropic coi ví dụ là một trong những cách đáng tin nhất để điều khiển định dạng, tone và cấu trúc; nên dùng 3–5 ví dụ liên quan, đa dạng, bọc trong tag <example>. Vẫn phải eval thêm vì ví dụ tăng độ nhất quán chứ không làm mọi response đúng. Q23
  • Agent sửa test bằng cách hard-code đúng input của test: sửa prompt theo mẫu của Anthropic — yêu cầu giải pháp tổng quát cho mọi input hợp lệ, không hard-code, nói rõ test dùng để kiểm chứng tính đúng chứ không định nghĩa lời giải, và nhờ Claude báo khi test sai hoặc yêu cầu vô lý. Giấu test hay thêm test không chữa được hành vi. Q30
  • PDF: đặt tài liệu trước instruction và câu hỏi (cùng tinh thần với long-context prompting), và tham chiếu trang theo số trang logic như PDF viewer hiển thị, không theo số in ở footer — tài liệu có phần đầu đánh số La Mã sẽ lệch vài trang. Đổi PDF sang plain text làm mất bảng, biểu đồ, layout. Q19
  • Giữ danh tính nguồn khi so sánh nhiều tài liệu: mỗi PDF là một document block riêng có title, bật citations cho cả hai, đặt câu hỏi sau tài liệu; rồi yêu cầu gắn mỗi phát hiện với title tài liệu và kiểm trong code rằng đoạn được trích đúng là của tài liệu đó. Gộp hai PDF vào một block là xóa ranh giới. Q40
  • Vision: khi nhãn phụ thuộc layout (badge ở panel nào, nút có bị làm mờ không), gửi ảnh chụp như image content block trong cùng user message với ticket và instruction, ở độ phân giải đủ đọc rõ. OCR chỉ bắt chữ; Files API chỉ có tác dụng khi request tham chiếu file_id. Q16

3. Tool use & structured output

  • Khi nào cần tool? Theo hướng dẫn tool use: hành động có side effect, dữ liệu mới hoặc bên ngoài, output cần đúng shape, gọi vào hệ thống có sẵn. Tóm tắt hay dịch thì Claude tự làm được, bọc thành tool chỉ thêm round trip (tool dịch còn gọi thêm một model nữa). Tín hiệu rõ nhất: nếu bạn viết regex để trích một quyết định từ output thì quyết định đó đáng lẽ phải là tool call hoặc field trong schema. Q4
  • Vòng lặp client tool: stop_reason: tool_use nghĩa là Claude nhờ ứng dụng chạy tool. Ứng dụng chạy tool với input của block, rồi gửi một user message mới chứa tool_result có tool_use_id khớp với id của block, và gọi lại API. Text trước tool call thường chỉ là Claude báo sắp làm gì, không phải câu trả lời. API không bao giờ chạy client tool. Q26
  • Client tool vs server tool: web search là server tool — Anthropic chạy search, citations luôn bật, mỗi citation có URL, title, đoạn trích. Dữ liệu riêng chỉ backend tới được thì cần client tool tự định nghĩa, backend chạy query và trả tool_result. Đặt tên tool tự viết là web_search không biến nó thành server tool. Q53
  • Strict tool use (strict: true) đảm bảo tham số tool call khớp input schema — điều khiển cách Claude gọi hàm. JSON outputs (output_config.format) đảm bảo response cuối khớp schema — điều khiển Claude nói gì. Hai tính năng bổ trợ nhau và dùng chung được trong một request. Q34
  • Giới hạn độ phức tạp tính trên tổng mọi schema strict trong một request (cả tool schema lẫn JSON output schema): tối đa 24 tham số optional, 20 tool strict, ngoài ra còn giới hạn union type. Mỗi schema hợp lệ riêng lẻ vẫn có thể cộng lại vượt ngưỡng. Cách giảm: chỉ đặt strict cho tool quan trọng, chuyển tham số có default hợp lý thành required, làm phẳng cấu trúc lồng, hoặc chia tool sang request khác. Q15
  • Đường thất bại của validation phải tường minh: retry có giới hạn, sửa (repair), hoặc fallback; chỉ chuyển đi bản ghi đã qua validation, hết lượt thì trả lỗi có kiểm soát. Phục hồi phải theo nguyên nhân: structured output có thể không khớp schema khi response là refusal hoặc dừng ở max_tokens — bị cắt thì retry với giới hạn cao hơn, refusal thì xử lý khác. Q39
  • Vòng agent không có điểm dừng (chỉ thoát khi end_turn): thêm bộ đếm vòng và lỗi max-turns tường minh, đồng thời vẫn trả lỗi tool về cho Claude dạng tool_result với is_error: true để nó retry hoặc đổi cách. Agent SDK có sẵn max_turns và result subtype error_max_turns. Q14

4. Kiến trúc agent, workflow & Managed Agents

  • Workflow hay agent? Quy trình cố định, biết trước → workflow được code sẵn (dễ đoán, nhất quán); việc mở, không lập kế hoạch trước được → agent. Kiểm tra tất định như validate JSON schema phải nằm trong code, chỉ gọi Claude ở bước cần hiểu ngôn ngữ, và workflow tự log từng bước để audit không phụ thuộc model nhớ ghi. Prompt chaining gần đúng nhưng cổng kiểm giữa các bước phải là code. Q6
  • Orchestrator + subagent: yêu cầu gộp nhiều mảng (hồ sơ, học bổng, nhà ở) theo thứ tự thay đổi, mỗi mảng cần tool và chuyên môn riêng → orchestrator chia việc cho subagent chuyên biệt và hợp nhất kết quả. Trong Agent SDK, mỗi subagent có context, prompt và giới hạn tool riêng, chỉ trả về kết quả nên không làm chật hội thoại chính. Orchestrator vẫn chịu trách nhiệm theo dõi hoàn thành. Q3
  • Subagent còn là kỹ thuật quản lý context: tra cứu trạng thái tài khoản trong subagent có context riêng, chỉ trả về trạng thái hiện tại đã xác minh kèm nguồn, nên agent chính không bao giờ thấy các trạng thái cũ. Q17
  • State graph khi có các giai đoạn, tiêu chí riêng từng giai đoạn và đường quay lại có điều kiện (thiếu bằng chứng thì quay về extraction). Framework như LangGraph mô hình bằng StateGraph với conditional edges. Anthropic khuyên hiểu framework làm gì bên dưới và test từng chuyển tiếp. Q44
  • Claude Managed Agents: Anthropic chạy agent loop, thực thi tool và lưu event history của từng session phía server, nên user có thể đóng trình duyệt rồi quay lại lấy kết quả. Môi trường chạy tool là lựa chọn riêng: cloud sandbox hoặc self-hosted sandbox (cho compliance, data residency). Q20
  • Memory store là tập tài liệu theo workspace, gắn vào session và hiện ra như một thư mục agent đọc/ghi bằng file tool — không được nạp sẵn vào prompt. Nên dùng store tập trung, ví dụ một store mỗi user/khách hàng để cô lập về cấu trúc; mỗi thay đổi tạo version bất biến để audit, có thể redact. Claude không tự nhớ gì giữa các session. Q20, Q35

5. Quản lý context, token & prompt caching

  • Đếm token đúng cách: gửi toàn bộ request (system prompt, tool, ảnh) tới token counting endpoint cho đúng model đích, rồi cộng phần output dự trữ trước khi so với giới hạn. Model mới có tokenizer khác, có thể ra nhiều token hơn cho cùng văn bản; chia ký tự cho 4 hay tokenizer bên thứ ba đều sai. Prompt vượt context window không bị API cắt mà lỗi 400. Q5
  • Context awareness: Claude Sonnet 5, Sonnet 4.6 và một số model trước tự theo dõi context còn lại — API đưa tổng budget vào system prompt và cập nhật dung lượng còn lại sau mỗi tool call. Tự động, không có tham số bật, và bạn không bao giờ tự gửi các tag đó. Một số model mới không nhận tag này và dùng task budget thay thế. Q10
  • Context lớn hơn không chữa được mất tập trung. Context window cỡ nào cũng bị "ô nhiễm" trong tác vụ dài. Công cụ đúng: compaction (tóm tắt lịch sử cũ thành một block thay thế, giữ nguyên văn các turn gần), tool result clearing (xóa output cũ khi vượt ngưỡng), ghi chú có cấu trúc và subagent. Bản tóm tắt phải giữ rõ mục tiêu, ràng buộc và phát hiện dang dở. Prompt caching chỉ giảm chi phí, không đổi cái gì ở lại context. Q12
  • Context editing + memory: xóa các kết quả CRM cũ khi context vượt ngưỡng token; kết quả bị xóa thay bằng placeholder, nên phải lưu các sự kiện đã xác minh còn cần vào memory file trước. Q17
  • Kết quả MCP quá lớn được lưu ra file và tool result thay bằng thông báo chứa đường dẫn — không mất dữ liệu, agent đọc lại được. Text dài hơn 50.000 ký tự cũng bị lưu ra file trừ khi tool khai báo anthropic/maxResultSizeChars (tối đa 500.000 ký tự), độc lập với MAX_MCP_OUTPUT_TOKENS. Q18
  • Chọn TTL theo khoảng cách tái sử dụng. Cache 1 giờ dành cho prompt dùng thưa hơn mỗi 5 phút nhưng dày hơn mỗi giờ (như chat mà user trả lời sau 10–30 phút): đặt ttl 1h trong cache_control. Prompt dùng nhiều lần mỗi phút giữ cache 5 phút, được refresh miễn phí; ghi cache 1 giờ đắt hơn. Khi trộn TTL, entry TTL dài phải đứng trước entry ngắn. Q13
  • Caching chỉ hoạt động trên prefix giống hệt nhau tới breakpoint. Đặt phần lặp lại (policy, system prompt) ở đầu request, giữ nguyên văn; đặt sau phần thay đổi thì không tái sử dụng được gì. Caching dùng được cùng Message Batches. Q48

6. Messages API, SDK & xử lý response

  • Đọc stop_reason trước khi hiển thị hay parse. max_tokens = chạm giới hạn đặt trong request, output chưa hoàn chỉnh → tăng max_tokens hoặc xin continuation. end_turn = model tự kết thúc. stop_sequence = khớp stop sequence tùy chỉnh (response nêu chuỗi khớp). model_context_window_exceeded = sinh output chạm context window. Khối usage giúp xác nhận (80 output token đúng bằng giới hạn). Q8
  • Streaming với extended thinking: reasoning đến qua sự kiện thinking_delta (trong thinking block riêng), không nằm trong text_delta. Ngay trước khi thinking block đóng có signature_delta; phải giữ thinking block kèm signature trong message đã lưu để multi-turn tool use hoạt động. Display omitted thì không có text thinking nào được stream. Q11
  • SDK vs REST thô: SDK chính thức tự gửi header xác thực, version, content-type, trả model có kiểu, tự retry (lỗi kết nối, rate limit, lỗi server có backoff) và có helper như accumulation khi stream. Không có SDK thì mỗi request phải có API key, header anthropic-version và content-type: application/json với body JSON — đúng những gì SDK làm bên dưới. Helper như get_final_message chỉ có trong SDK. Q21
  • Backend tự động, không người tham gia, cần truyền tool definition và xử lý tool_use → Messages API qua Python SDK. Claude Desktop là app cho người; Claude Code headless dành cho chạy chính Claude Code trong script/CI với tool file và shell. Q46
  • Messages API là stateless: mỗi request chứa toàn bộ hội thoại mà Claude thấy, ứng dụng quyết định gửi gì. Rò rỉ giữa user xảy ra khi ứng dụng gửi một history chung. Sửa: lưu history riêng theo user và hội thoại, chỉ nạp sau khi kiểm tra user đã xác thực là chủ sở hữu. User ID trong request không tạo history phía server. Q37
  • Đọc mã lỗi HTTP: 400 invalid_request_error (request sai, prompt quá dài), 401 authentication_error (key sai/bị thu hồi), 403 permission_error (key không có quyền với tài nguyên), 429 rate_limit_error. File của Files API thuộc phạm vi workspace; key chạy ở workspace khác thì gọi thường vẫn được nhưng dùng file của workspace kia bị 403. Q45

7. Claude Code, Agent SDK & MCP

  • CLAUDE.md đặt ở đâu? CLAUDE.md ở gốc repo được nạp đầy đủ mỗi phiên trong repo đó, chia sẻ qua version control, không ảnh hưởng repo khác — chỗ của lệnh build/test, coding standard, quyết định kiến trúc. ~/.claude/CLAUDE.md áp cho mọi project của user. CLAUDE.local.md là tùy chọn cá nhân, nên gitignore. Permission rule trong .claude/settings.json không mang chỉ dẫn. Q36
  • Giữ CLAUDE.md gọn (dưới 200 dòng, chỉ phần thiết yếu): quy trình chuyên biệt dùng thưa (migration, release, review PR) chuyển sang skill, chỉ nạp khi được gọi. Với ngôn ngữ có kiểu, cài code intelligence plugin để đi tới định nghĩa thay vì grep rồi đọc nhiều file ứng viên; language server còn báo lỗi kiểu sau khi sửa. Q31
  • Hook tiền xử lý dữ liệu: PreToolUse hook trên Bash bọc lệnh test để chỉ lọc ra failure và error trước khi Claude thấy — giảm context từ hàng chục nghìn token xuống hàng trăm mà không đổi lệnh test. Lời dặn trong CLAUDE.md hay output style không thu nhỏ được tool result vì token đã tốn lúc output vào hội thoại. Q25
  • Làm việc với dịch vụ ngoài: bảo Claude dùng CLI như gh, aws, gcloud, sentry-cli — cách tiết kiệm context nhất. Cài và xác thực gh để tránh rate limit của request ẩn danh; Claude học CLI lạ qua --help. Q22
  • Skill trong Agent SDK: SDK tự thêm tool Skill vào allowedTools, nhưng nếu bạn truyền danh sách tools tường minh thì phải thêm Skill vào đó, nếu không skill được phát hiện mà không gọi được. Q27
  • Chạy Claude Code trong pipeline: -p (non-interactive), cấp sẵn đúng tool cần qua --allowedTools hoặc permission rule, lấy kết quả bằng --output-format json (result, session ID, metadata); --json-schema nếu cần shape cố định. Q47
  • Plugin bên thứ ba chạy code trên máy dev với quyền của dev (hook, MCP server) và thêm chỉ dẫn vào context. Trước khi triển khai: kiểm nguồn marketplace, review component và source, duyệt một phiên bản pin cố định, rồi dùng managed settings để allowlist nguồn marketplace cho cả tổ chức. Q43
  • MCP primitive: resource là nguồn dữ liệu thụ động, read-only, có URI để client list và read làm context; tool là hàm model gọi để thực hiện thao tác, có inputSchema; prompt là template chỉ dẫn tái sử dụng do user chọn. Catalog có version → resource; chấm điểm rủi ro → tool. Q33
  • Chọn cơ chế mở rộng theo phạm vi chức năng, nhu cầu tái sử dụng, bối cảnh tích hợp và trách nhiệm bảo trì. Skill = chỉ dẫn, kiến thức, workflow nạp khi liên quan (playbook); MCP = kết nối tool và dịch vụ ngoài dùng chung (lookup live cho ba app); custom tool đơn giản cho việc một lần. Q42

8. Evaluation, testing & phát hành

  • Rollout theo giai đoạn với ngưỡng rollback định trước. Đưa một phần nhỏ traffic thật (2%) sang bản mới, đo độ chính xác trên mẫu đã review, chỉ mở rộng khi ngưỡng còn giữ. Vừa giới hạn số khách bị ảnh hưởng, vừa phơi model trước ngôn ngữ/loại đính kèm mà bộ offline thiếu. Shadow mode đo đồng thuận với bản cũ, không phải độ chính xác. Q7
  • Điểm tổng che giấu lỗi tập trung ở một slice nhỏ: slice adversarial cần ngưỡng riêng, launch cho cohort nhỏ, thêm model nhẹ sàng lọc input phía trước (mẫu harmlessness screen — lớp kiểm soát độc lập thứ hai), theo dõi output bị gắn cờ và có rollback đã test. Q41
  • Hai bản prompt tranh cãi → chạy cả hai cùng prompt hiện tại trên bộ held-out đại diện, chấm theo tiêu chí định trước (accuracy, completeness, latency), chọn bản tốt nhất. Gộp hai bản là tạo prompt thứ ba chưa test; A/B live chỉ dùng sau khi eval offline đã thu hẹp lựa chọn. Q50
  • Quản lý phiên bản prompt: prompt bất biến có version, lưu kèm kết quả eval, các service đọc version do release pointer chỉ định, log version dùng cho mỗi request. Rollback chỉ là dời pointer — vài phút, không cần deploy. Q49
  • Chiến lược test nhiều tầng: unit test cho hàm tất định (dựng request, validate lịch), integration test cho tương tác với Claude và đường lỗi API, end-to-end test cho hành trình đặt chỗ quan trọng. Eval model nằm bên cạnh các phương pháp khác, không thay thế. Q28

9. Bảo mật, guardrails & dữ liệu

  • Tuân thủ không được phụ thuộc phán đoán của model → cổng bằng code. PreToolUse hook chạy trong code ứng dụng trước khi tool thực thi, kiểm host với danh sách duyệt và change window đọc trực tiếp từ hệ thống lịch, trả quyết định deny kèm permissionDecisionReason để Claude đề xuất phương án hợp lệ. Hook được đánh giá đầu tiên trong thứ tự permission của SDK. System prompt, ask rule cho người duyệt hay subagent reviewer đều vẫn là phán đoán. Q9
  • Indirect prompt injection: nội dung bên thứ ba chỉ đưa vào trong tool_result, ghi rõ nguồn (URL), không bao giờ vào system prompt hay text user thường; Claude được huấn luyện để hoài nghi chỉ dẫn trong tool result. Hành động hệ trọng (thanh toán) phải có cổng code: payee trong danh sách duyệt + người phê duyệt. Q24
  • Giảm dữ liệu gửi đi là kiểm soát thật sự: classifier chỉ cần nội dung ticket thì chỉ gửi nội dung đó, redact định danh; dữ liệu đã lưu đặt ở workspace hạn chế với thời hạn lưu xác định. Mã hóa at rest không ngăn người có quyền đọc; lời dặn trong prompt không cưỡng chế được xử lý dữ liệu. Q32
  • Ranh giới giữa user nằm trong code ứng dụng, không trong lời dặn: dữ liệu không được tới context của một user thì ứng dụng phải loại ra trước. Q37
  • API key: nạp lúc runtime từ biến môi trường hoặc secrets manager, không bao giờ commit; quét repo tìm secret. Key đã lọt vào history phải revoke và thay, vì xóa khỏi commit mới nhất không xóa được lịch sử. .env đã commit hay Base64 đều không bảo vệ gì. Q51

13. Mẹo làm bài thi

  • Hỏi "cái này có phụ thuộc phán đoán của model không?" Đề nào có chữ must not depend on, never, guarantee thì loại mọi đáp án chỉ là lời dặn trong prompt, CLAUDE.md hay một model reviewer khác. Đáp án đúng gần như luôn là code: hook, schema, allowlist, phân tách dữ liệu.
  • Đọc tín hiệu trong JSON/code của đề. stop_reason, khối usage, mã HTTP, vòng while True chỉ thoát ở end_turn — chi tiết nhỏ này thường đủ để gạch 2–3 đáp án.
  • "Lớn hơn" hiếm khi là đáp án. Context window lớn hơn, max_tokens cao hơn, model mạnh hơn, thêm test hơn đều chỉ hoãn hoặc che vấn đề. Tìm đáp án chạm đúng nguyên nhân.
  • Câu "Select two" thường là hai nửa bổ trợ. Ví dụ: strict tool use cho tool call + JSON outputs cho response cuối Q34; tool_result cho nội dung web + cổng code cho thanh toán Q24; cache + batch Q48; server tool + client tool Q53.
  • Eval trước, ship sau. Mọi lựa chọn model, prompt hay rollout đều nên dựa trên bộ eval đại diện theo tiêu chí định trước. Đáp án nào "ship ngay", "chuyển ngày ra mắt" hay "dựa vào benchmark công khai" thường sai.
  • Phân biệt chi phí với chất lượng context. Prompt caching và batch giảm tiền; compaction, clearing, subagent giảm nhiễu. Đề hỏi "mất tập trung" mà đáp án là caching là bẫy.
  • Chọn đúng nơi đặt thứ gì. Chỉ dẫn → CLAUDE.md hoặc skill; quyền → permission rule; cưỡng chế → hook; dữ liệu bên thứ ba → tool_result; credential → secrets manager.
  • Ít dữ liệu hơn là an toàn hơn. Khi đề hỏi giảm rủi ro rò rỉ, đáp án tốt nhất là không gửi/không lưu dữ liệu không cần, chứ không phải mã hóa hay dặn model.

14. Bẫy thường gặp

  • Prompt caching không làm ràng buộc cũ nổi bật hơn, cũng không loại bỏ dữ liệu cũ. Nó chỉ làm rẻ hơn việc gửi lại. Q12, Q17
  • max_tokens là trần cho một response, không giới hạn số vòng lặp, không giúp Claude "đọc" tài liệu nhiều hơn, không giảm chi phí và không phải số token bị tính tiền. Q14, Q19, Q38, Q48
  • Messages API không có bộ nhớ hội thoại. Claude không tự nhớ gì giữa các request hay session; muốn nhớ phải gửi lại history hoặc dùng memory store. Q35, Q37
  • API không tự cắt prompt quá dài — nó trả 400. model_context_window_exceeded chỉ xảy ra khi đang sinh output. Q5, Q8
  • Cache 1 giờ đắt hơn khi ghi, không rẻ hơn; và khi trộn TTL, entry dài đứng trước. Q13
  • Streaming không giảm số token bị tính tiền. Q48
  • Giới hạn schema strict tính trên tổng, không phải từng schema; và giới hạn tool là 20 chứ không phải 5. Q15
  • Shadow mode đo đồng thuận, không đo độ chính xác. Q7
  • ID model không ngày của thế hệ 4.6 không phải pointer tự cập nhật; alias của model cũ mới là thứ có thể đổi ngầm. Q52
  • CLAUDE.local.md không chia sẻ được với team (nên gitignore). Q36
  • Đặt tên client tool là web_search không biến nó thành server tool. Q53
  • Base64 là encoding, không phải mã hóa; file .env đã commit không còn bí mật. Q51
  • Mã hóa at rest không giới hạn những người được phép đọc. Q32
  • Output style và lời dặn không thu nhỏ được tool result — token đã tốn khi output vào hội thoại. Q25

CâuĐáp án sai & vì sao sai
Q1
  • Chọn model mạnh nhất trước rồi mới xác định yêu cầu: model tier không định nghĩa input, output hay phụ thuộc của sản phẩm; chọn trước là đảo ngược quy trình dựa trên yêu cầu
  • Bắt chước mẫu triển khai của nhà xuất bản khác: tiền lệ phục vụ ràng buộc của bên khác, không thể thay thế yêu cầu của chính tính năng này
  • Chọn framework trước rồi viết lại mục tiêu cho khớp: bẻ nhu cầu nghiệp vụ cho vừa công cụ; công cụ phải khớp mục tiêu chứ không ngược lại
Q2
  • Viết hoa ACCURATELY nhiều lần: nhấn mạnh không bổ sung thông tin còn thiếu, Claude vẫn không biết mã nhãn nghĩa là gì, còn có thể khiến model thận trọng thái quá
  • Tăng temperature: chỉ thêm ngẫu nhiên, nhãn hiếm bị chọn lung tung hơn chứ không đúng hơn; model mới còn có thể từ chối tham số sampling không mặc định
  • Bỏ hết hướng dẫn, để người duyệt kết quả độ tin cậy thấp: Claude càng ít căn cứ, review chỉ bắt lỗi sau khi đã xảy ra, gốc vấn đề (mã mờ nghĩa) vẫn còn
Q3
  • Cho agent chung tất cả tool chuyên biệt, giữ một history: thêm tool không tách context hay phân trách nhiệm, giữ nguyên kiến trúc đang bị mất dấu
  • Mọi yêu cầu đi qua cùng một chuỗi cố định: chuỗi cố định chỉ hợp khi thứ tự đoán trước được; ở đây vấn đề và thứ tự thay đổi, nhiều bước là thừa
  • Dặn agent tự giữ checklist: có ích cho theo dõi nhưng mọi việc chuyên biệt vẫn dồn trong một context chung
Q4
  • Bọc mọi năng lực còn lại thành tool để audit: thêm round trip và độ phức tạp, ngược với vấn đề latency; audit log ghi được cả reply thường
  • Giữ regex nhưng nới lỏng hơn: đổi bỏ sót lấy khớp nhầm, vẫn giữ bước parse mong manh; regex trích quyết định là dấu hiệu quyết định đó thuộc về schema
  • Đưa thao tác hoàn tiền vào system prompt: lời dặn không cập nhật được billing; hành động có side effect bắt buộc cần tool
Q5
  • Hiệu chỉnh hệ số chia ký tự theo từng model: vẫn là một tỉ lệ trung bình, tài liệu sát ngưỡng vẫn bị đoán sai, và bỏ qua phần token của tool và ảnh
  • Bỏ guard, để API tự cắt nội dung cũ: API không cắt prompt quá lớn mà trả 400 invalid_request_error; model_context_window_exceeded là chuyện khác, xảy ra khi đang sinh output
  • Dùng tokenizer mã nguồn mở trên phần thân tài liệu: không khớp tokenizer của Claude, và bỏ sót system prompt, tool, ảnh
Q6
  • Một agent có đủ tool, system prompt liệt kê 4 bước: agent vẫn tự quyết gọi tool nào tiếp theo nên đường đi không được đảm bảo; log phụ thuộc model nhớ ghi
  • Orchestrator-workers lên kế hoạch cho từng hồ sơ: mẫu này dành cho subtask không đoán trước; ở đây 4 bước cố định nên chỉ thêm chi phí và biến động
  • Chuỗi 4 lời gọi Claude, lời gọi thứ hai kiểm schema: gần đúng nhưng kiểm schema phải là cổng lập trình tất định, không phải một lời gọi model
Q7
  • Mở rộng bộ eval offline rồi chuyển toàn bộ traffic: bộ offline luôn đi sau traffic thật, và regression bị sót sẽ chạm cả 200.000 ticket/ngày cùng lúc
  • Shadow mode, chuyển khi hai classifier đồng ý ≥90%: đồng thuận với bản cũ không phải độ chính xác, bản mới đúng mà bản cũ sai lại bị tính là lỗi; bước cuối vẫn chuyển hết một lần
  • Thay toàn bộ, rollback khi dưới 90%: mọi ticket đã nằm trên bản mới trước khi mẫu hằng ngày phát hiện; dùng ngưỡng offline làm ngưỡng rollback có thể kích hoạt muộn
Q8
  • Chạm context window nên turn cũ bị bỏ: chạm context window cho stop reason model_context_window_exceeded, không phải max_tokens; 920 input token còn rất xa giới hạn
  • Model tự kết thúc ngắn, thêm yêu cầu độ dài tối thiểu: tự kết thúc sẽ báo end_turn; đây là bị cắt, thêm yêu cầu dài hơn càng dễ bị cắt
  • Stop sequence đã khớp, gỡ stop sequence: khi đó stop_reason là stop_sequence kèm chuỗi khớp; gỡ đi không chạm tới giới hạn 80 token thật sự gây cắt
Q9
  • Nạp danh sách host và change window vào system prompt: vẫn là hướng dẫn model tự diễn giải, không gì ngoài model chặn được lời gọi sai; window có thể đổi giữa phiên nên bản sao bị cũ
  • Ask rule cho operator duyệt từng hành động: tuân thủ lại dựa vào phán đoán của con người, và làm chậm cả các hành động thường lệ
  • Subagent reviewer kiểm tra trước khi chạy: vẫn là một model phán đoán; yêu cầu là tuân thủ không được phụ thuộc phán đoán của model
Q10
  • Claude không theo dõi được context còn lại: sai với Sonnet 5, API đã cung cấp budget và cập nhật sau mỗi tool call; model không có context awareness thì dùng task budget
  • Ghi chú phải dùng định dạng tag system_warning: tài liệu nói bạn không bao giờ tự gửi các tag này, API tự chèn; tự sao chép tạo tín hiệu budget thứ hai có thể mâu thuẫn
  • Phải bật context awareness bằng tham số request: context awareness là tự động, không có tham số nào, và hoạt động qua thông tin API chèn vào chứ không qua Claude báo cáo
Q11
  • Lọc dòng bắt đầu bằng "Thinking:" trong text_delta: reasoning tóm tắt không nằm trong text_delta mà stream qua thinking_delta trong thinking block riêng
  • Gọi thêm một lần non-streaming với display full: gấp đôi chi phí và độ trễ, reasoning lại mô tả một response khác với cái user đã thấy
  • Đặt thinking display là omitted: khi đó không có text thinking nào được stream (thinking_delta rỗng), panel sẽ trống; signature vẫn đến và vẫn cần giữ
Q12
  • Bật prompt caching cho toàn bộ history: caching chỉ giảm chi phí input lặp lại, không đổi message nào ở lại context hay làm ràng buộc cũ nổi bật hơn
  • Khởi động lại agent sau mỗi 7 lời gọi, bỏ state: phiên mới không biết ràng buộc và phát hiện dang dở, sẽ làm lại việc hoặc vi phạm yêu cầu cũ
  • Chọn context window lớn hơn, giữ nguyên mọi output: vấn đề là mất tập trung chứ không phải hết chỗ; giữ nguyên output chính là điều kiện gây lỗi
Q13
  • Chuyển cả hai workload sang TTL 1 giờ vì rẻ hơn: cache 1 giờ ghi đắt hơn chứ không rẻ hơn; classifier vốn đã refresh cache 5 phút liên tục
  • Giữ TTL 5 phút, ping làm ấm mỗi 4 phút: thêm request và tải cho mỗi chat rảnh, lỡ một ping là mất cache; TTL 1 giờ sinh ra cho đúng khoảng trống này
  • Đặt breakpoint 5 phút trước breakpoint 1 giờ: khi trộn TTL, entry TTL dài phải đứng trước entry ngắn; entry 5 phút không "bảo vệ" được entry 1 giờ
Q14
  • Trả về ngay khi stop_reason là tool_use: tool_use nghĩa là Claude đang nhờ chạy tool, chưa xong việc; giới hạn đạt được bằng cách tước luôn khả năng hành động
  • Tăng max_tokens để Claude suy luận xử lý lỗi: max_tokens giới hạn độ dài một response, không giới hạn số vòng lặp; lỗi đến từ tool nên suy luận dài hơn không sửa được
  • Ném exception ngay ở lỗi tool đầu tiên: có chặn được vòng lặp nhưng bỏ mất đường phục hồi; lỗi thoáng qua cũng kết thúc run, đẩy việc replay thủ công cho on-call
Q15
  • Mỗi schema strict được kiểm riêng nên schema mới có lỗi ẩn: giới hạn tính trên tổng tất cả schema strict trong request; viết lại mà không giảm tham số optional vẫn lỗi
  • Strict mode tối đa 5 tool mỗi request: giới hạn thật là 20 tool strict; 6 tool còn xa, nguyên nhân là tổng tham số optional
  • Giới hạn chỉ áp cho JSON output schema: áp cho cả tool schema lẫn output schema; dời output schema vào tool không làm giảm tổng
Q16
  • Giữ OCR, thêm tọa độ bounding box: OCR chỉ bắt chữ, nút bị làm mờ hay badge màu không có chữ thì không bao giờ xuất hiện
  • Upload ảnh qua Files API rồi để Claude tự ghép ticket: file upload không có tác dụng nếu request không tham chiếu file_id trong content block; Claude không tự duyệt file
  • Nhờ nhân viên mô tả ảnh bằng chữ: thay bằng chứng bằng diễn giải của người, dễ sót badge nhỏ, thêm việc thủ công và bỏ phí khả năng vision
Q17
  • Giữ hết kết quả, dặn Claude ưu tiên bản mới nhất: mọi kết quả cũ vẫn nằm trong context, vẫn dựa vào Claude tự phân xử, đúng tình huống đã gây lỗi
  • Bật prompt caching và gắn timestamp: kết quả cũ rẻ hơn khi gửi lại nhưng vẫn nằm trong context; tối ưu chi phí mà giữ nguyên nguyên nhân lỗi
  • Tóm tắt định kỳ nhưng chép nguyên văn mọi kết quả: trạng thái cũ chỉ chuyển sang nằm trong bản tóm tắt; tóm tắt tốt phải bỏ cái đã lỗi thời
Q18
  • MCP server bị crash và ghi file crash: lưu ra file là cách xử lý kết quả lớn có tài liệu; tool call thành công, thu hẹp khoảng ngày chỉ làm mất dữ liệu
  • Chỉ cần nâng MAX_MCP_OUTPUT_TOKENS trên 40.000: còn ngưỡng 50.000 ký tự riêng cho text, áp dụng trước, trừ khi tool khai báo anthropic/maxResultSizeChars
  • File là cache tạm hết hạn sau vài giây: tài liệu mô tả file để agent đọc lại từng phần, không có chuyện hết hạn; chép file trước mỗi lời gọi là vô căn cứ
Q19
  • Chuyển PDF sang plain text: mất biểu đồ, bảng và layout mà Claude phân tích được ở dạng PDF, và lỗi số trang vẫn còn
  • Đưa số trang và định dạng footer vào system prompt: bắt Claude dịch giữa hai cách đánh số, thêm chỗ sai; dùng số trang logic thì khỏi phải dịch
  • Tăng max_tokens để Claude có chỗ "tìm" trang: max_tokens giới hạn độ dài response, không liên quan việc đọc input; PDF đã nằm trọn trong request
Q20
  • Web server của team phải chạy agent loop và giữ kết nối: đó là mô tả xây trên Messages API; Managed Agents chạy loop và lưu event phía server để user quay lại lấy
  • Memory store là context window mở rộng, nạp sẵn vào prompt: memory store được mount thành thư mục, agent đọc/ghi bằng file tool, không nạp sẵn vào prompt
  • Chỉ chạy trên sandbox cloud của Anthropic: Managed Agents hỗ trợ self-hosted sandbox cho nhu cầu compliance và data residency, không cần quay về Messages API
Q21
  • Thiết bị bỏ header anthropic-version cho API tự suy: header này bắt buộc khi gọi trực tiếp, thiếu thì request bị từ chối
  • Phải serialize qua class của SDK: endpoint nhận mọi JSON hợp lệ có đúng header; class của SDK chỉ là tiện ích
  • Hai bên nhận cùng object có helper như get_final_message: REST trả JSON thô, helper chỉ có trong SDK; code parse viết theo SDK không chạy được trên thiết bị
Q22
  • Dán tay nội dung issue vào prompt: đẩy việc sang developer, Claude vẫn không mở được PR hay đọc comment, prompt phình to và dễ cũ
  • Cho Claude scrape trang web GitHub: kéo thêm markup vào context, dễ vỡ khi trang đổi, không có cách có xác thực để mở PR
  • Hook chặn mạng để Claude dùng dữ liệu huấn luyện: dữ liệu huấn luyện không có issue hiện tại của repo, triage thành bất khả thi
Q23
  • Chỉ dùng ví dụ để cấu hình validator sau inference: validator kiểm sau khi sinh, không cho Claude thấy mẫu biến đổi lúc đang tạo response
  • Zero-shot dựa vào kiến thức chung: bản nháp zero-shot đã lệch thứ tự section, lại bỏ phí 4 cặp ví dụ đã duyệt
  • Huấn luyện một model riêng: thêm cả một quy trình phát triển model trong khi chỉ cần minh họa định dạng; bốn ví dụ trong prompt đã đủ
Q24
  • Dán nội dung trang vào system prompt với tiêu đề "untrusted": system prompt là chỗ của chỉ dẫn tin cậy, đặt nội dung kẻ tấn công vào đó trao cho nó quyền cao nhất
  • Dặn Claude từ chối yêu cầu thanh toán trong web, dùng làm control chính: phụ thuộc Claude nhận ra mọi injection; yêu cầu "không bao giờ" cần cưỡng chế bên ngoài model
  • Cho tool tài chính quyền đảo ngược thanh toán: chỉ là phục hồi sau khi tiền đã đi, có giao dịch không đảo được, lại cấp thêm quyền cho agent
Q25
  • Dặn trong CLAUDE.md chỉ đọc dòng lỗi: tool result vào hội thoại trước khi Claude đọc, token đã tốn; lời dặn không làm nhỏ output
  • Dùng model có context window lớn hơn: chỉ hoãn vấn đề, mỗi lần chạy vẫn tốn hàng chục nghìn token và tăng chi phí mọi request
  • Output style tóm tắt mỗi lần chạy thành một dòng: output style định hình câu trả lời của Claude, không phải tool result; output đầy đủ vẫn đã vào context
Q26
  • Hiển thị text block như câu trả lời cuối, không gọi tool: text trước tool call thường chỉ là Claude báo sắp làm gì; request sau sẽ lỗi vì tool_use thiếu result
  • Chèn output vào chính assistant message: tool result phải nằm trong user message dạng tool_result; sửa turn của assistant phá cấu trúc và bị API từ chối
